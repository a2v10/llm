# Виміри: спитати в конфігурації

**Жодне твердження про цю конфігурацію не береться з пам'яті, з чужого досвіду і з цього скіла.**
Правила в `analysis.md` і `kinds.md` описують, що буває; скільки цього тут — рахується тут.

Правило народилося не з педантизму: у специфікації виміряне не відрізнити від правдоподібного, а
за місяць перевіряти дорожче, ніж було порахувати.

## Скрипти

Лежать у `scripts/`, чистий Python 3 без залежностей. Дамп вони лише читають і нічого в ньому не
змінюють.

| питання | скрипт | що дивитися у відповіді |
|---|---|---|
| що це за система, з чого складається | `overview.py` | склад за видами, найбільші об'єкти, підсистеми, що є понад оголошення |
| що входить у розділ обліку | `section.py` | документи в складі підсистем, відкриті командами повз склад, кандидати з журналів |
| що приходить до подій розділу таблицею, а що колонкою | `closure.py` | довідники таблицями, документи чужих розділів колонками; посилання за межі дампу |
| що дамп пропонує вважати однією подією | `candidates.py` | найбільша компонента за кожною ознакою **окремо** |
| які сутності — предметне ядро | `refs.py` | вхідні посилання за об'єктами, а не за полями |
| чи живий реквізит | `readers.py` | нуль читачів або єдиний в оновленні бази |

```
python scripts/overview.py   --dump build --lang uk --out звіт.txt
python scripts/section.py    --dump build Покупки --lang uk --out закупівлі.txt
python scripts/closure.py    --dump build Document.Ім'я --perimeter perimeter.tsv
python scripts/candidates.py --dump build --reg-cap 3
python scripts/refs.py       --dump build --from Document --top 40
python scripts/readers.py    --source source/Configuration ІмʼяРеквізиту
```

Аргумент `section.py` — ключ підсистеми, як він записаний у `subsystems.json` (у цьому прикладі —
`Покупки`); імена 1С не перекладаються.

`readers.py` — єдиний, хто ходить у вивантаження: читачів шукають у модулях, а коду в дампі немає.
Він обходить усі модулі й працює хвилини, а не секунди; імена можна передавати пачкою, файли
читаються один раз на всі.

## Вимір пишеться у файл, а не в діалог

У всіх скриптів є `--out`. Повні списки, надруковані в листування, пересилаються кожним наступним
ходом і з'їдають контекст, заради якого все й затівалося. У розмову йдуть висновки й два-три числа,
файл лишається поруч.

## Як читати результат

**Ознака, що склеює половину, — не ознака.** Так улаштовано `candidates.py`: він рахує кожне ребро
**окремо** саме для того, щоб це було видно. Якщо одна ознака дає компоненту в половину документів,
вона виражає зручність введення чи перегляду, а не належність до події.

**Вимір, що не дав поділу, — це матеріал, а не відповідь.** «Механічно не виводиться» не означає
«не існує»: подія існує незалежно від того, чи знаходить її граф. З виміру випливає, що межу
проводить людина, і нічого більше.

**Посилання за межі дампу** в `closure.py` — це не помилка, а дві різні речі одразу: об'єкт поза
периметром або вид, який інструмент поки не читає. Розрізняти за списком видів, який інструмент
називає під час прогону.

## Чого в скриптах немає

Вони не пишуть у дамп, не правлять периметр і не приймають рішень. Файл периметра `closure.py`
генерує як **доповнення** того, що увійшло (інструмент віднімає, а не вибирає), — і це єдине, що він
виробляє, крім звіту.

Нове питання до конфігурації — це новий маленький скрипт поруч, а не міркування з пам'яті.
