# `rules` і `properties` — правила полів і властивості моделі

Два блоки-сусіди `fields` у своїй області. `fields` описує **сховище**; `rules` — **правила, що пов'язують поле з іншими полями того самого запису**: чи обов'язкове, чи видиме, звідки воно приїжджає по посиланню; `properties` — **чому дорівнює значення**: властивості моделі з get і, можливо, set (розділ «`properties`» нижче).

Те, що приходить ззовні запису, до жодного з них не належить: початкові значення — `initialValues`, канали вводу посилання — `lookup`, структура — `fields`.

## Де живе

Область задає **позиція**, як в `initialValues` і `lookup`: блок поруч із `fields` шапки — про поля шапки, блок усередині `details.<Collection>` — про поля рядків цієї колекції, блок усередині `details.<Collection>.kinds.<Kind>` — про поля рядків **цього виду** ([metadata.md](metadata.md) → «`kinds` — види рядків»).

Шари звичайні: власник таблиці (корінь `document/metadata.json`) і документ над `storage` (`document/<name>/metadata.json`). Документ пише `details.<Collection>.rules` (і `properties`) без shape-ключів — правило «документ над `storage` не повторює структуру» тримає схема.

🚧 Третій шар — операція (`<op>.operation.json`). Її `rules` і `properties` відхиляються при завантаженні, доки генератор не читає `when`: правила операції — це `when` з тестом по `this.Operation`, виведений зі структури, і шаруються вони за тими самими законами ([metadata.md](metadata.md) → «`document` — таблиця й операції»).

**Вид рядка — не третій шар, а друга вісь.** «Хто оголошує» (корінь / документ) і «про кого» (вся колекція / один вид) незалежні: документ має право уточнити правила одного виду, а корінь — оголосити спільні для всіх. Перетин дає чотири позиції, але політика злиття задається по кожній осі окремо, і вона в обох однакова (нижче).

Це документ над `storage`. У документа з власною таблицею ([metadata.md](metadata.md) → «`document` — таблиця й операції») шар один: `rules` стоять поруч зі своїми `fields` у тому самому файлі, шарувати нема чого.

### Як зливаються шари

Види шаруються **незалежно один від одного** — це дає інверсія ключа. А що відбувається **всередині** виду, з інверсії не випливає: це задає форма виду і те, про кого говорить нижній шар.

| Вид | Злиття | Чому так |
|---|---|---|
| `required` | **об'єднання** | список кореня означає «потрібно **кожному** документу над таблицею» — це твердження про всі документи, а не умовчання для них |
| `visible`, `inherit` | по ключу поля, верхній перекриває | видимість одного поля і видимість іншого — незалежні факти, які випадково діляться видом |
| `when` | 🟡 список документа заміщує список кореня | не рішення, а відкладення: `when` поки нікуди не приземляється, вирішувати його гранулярність нема на чому |

**Та сама таблиця працює на осі «колекція → вид рядка».** Вище колекція, нижче вид рядка: `required` колекції означає «потрібно кожному виду» і доповнюється, мапи перекриваються по ключу поля.

Перекриття мап — не поступка, а те, чим лікується **часткова спільність**. Три види рядків, у двох `Sum` рахується однаково, у третього інакше: спільна властивість стоїть на колекції, третій вид перекриває її своєю. Дублювати не доводиться, і слово «спільне» лишається за тим шаром, який справді говорить про всіх. `properties` шаруються тим самим законом, що мапи `rules`, на обох осях.

**Ослаблення не пишеться, і бракує тут не синтаксису.** Зняти `required`, оголошений коренем, документ не може, бо вимога, вірна не для всіх документів, у корені **неправильна** — вона чиниться переносом униз, у той документ, якому потрібна. Тест працює і як підказка: тягне написати «а в цьому документі не обов'язково» (або «а в цьому виді рядків не обов'язково») — оголошення стоїть не в тому шарі.

Ціна названа: зайву вимогу видно (валідатор у формі), а от `required`, який документ **не** дописав, не видно ніяк. Тому обміняли ми саме в цей бік — гучний відмову проти тихого.

## Одиниця оголошення — правило, а не поле

Ключ блоку — **вид правила**; імена полів лежать усередині нього.

```jsonc
"rules": {
  "required": ["StoreTo", "Agent"],
  "visible":  { "Discount": "this.Qty > 10" },
  "inherit":  { "Unit": { "ref": "Item", "field": "Unit" } }
}
```

Кожен вид має **власну форму**, а не спільну: `required` — просто імена, бо сказати про нього більше нічого; `visible` — ім'я і вираз; `inherit` — ім'я і два імені джерела. Жодна форма не прикидається іншою, і жодна не обіднена — вони повні, просто різні.

Три наслідки, і кожен раніше вимагав окремого правила в тексті:

1. **Параметр не може осиротіти.** Його місце — тільки всередині форми свого виду; спільного рівня, куди його впустити, не існує. Питання «а `applyIf` — це до чого?» не має синтаксису, щоб виникнути.
2. **Новий вид не чіпає сусідів.** У видів різні простори імен, взаємодіяти нічим — блок росте вшир безпечно.
3. **Одиниця шарування — вид.** Документ, який написав `required`, не торкається `visible` кореня: види шаруються незалежно, бо ключ — вид. **Політика злиття всередині виду звідси не випливає** — її задає форма виду, а форми різні за побудовою (пункт вище). Таблиця — у «Як зливаються шари».

**Зворотне прочитання відкинуте:** ключ = поле, значення = мішок його правил. Мішок змушує кожен новий параметр шукати хазяїна серед сусідів, а кожен новий вид — розширювати спільну форму, придатну для всіх; звідси і теги, і вкладені payload-об'єкти, і полiморфні значення. Усі три зникають від інверсії, а не від перебудови контейнера.

## Види правил

| Вид | Форма | Приземлення |
|---|---|---|
| `required` | `string[]` — імена полів | `validators` |
| `total` | `string[]` — імена полів **колекції** | `properties` на типі масиву (`$sum`) |
| `visible` | `{ <Field>: вираз }` | 🟡 `properties` шаблону (`$<Field>Visible`) — оголошується і зливається, але жоден генератор його ще не читає |
| `inherit` | `{ <Field>: { ref, field } }` | `events` `<ref>.change` |
| `when` | `[ { test, <види правил> } ]` | за видом усередині: `required` → `applyIf`, `visible` → getter із тернарним, `inherit` → `if` в обробнику; 🚧 жоден генератор не читає |

Імен `validators` / `events` у metadata немає — карту обирає генератор. Автор пише факт. `visible` і `total` приземляються в `properties` шаблону, але ім'я властивості дає **платформа** (`$DiscountVisible`, `TRowArray.Sum`) — тому вони правила, а не блок `properties`, де ім'я дає автор.

### `required` — повнота запису

Список імен, і більше в ньому нічого немає. Момент, коли вимога спрацьовує, дає kind: для каталогу — збереження, для документа — проведення ([metadata.md](metadata.md) → «`NOT NULL` і `required`»).

Шари **об'єднуються**: список кореня — те, що потрібно кожному документу над таблицею, і документ його доповнює, а не заміщує («Як зливаються шари»).

Дороги до `NOT NULL` немає: `NOT NULL` дає домен, не оголошення. На полі домену з нулем (`Qty`, `Amount`, `Boolean`, …) незаповнене — це нуль, тому `required` там означає «не 0» / «позначено» ([metadata.md](metadata.md) → «`NOT NULL`»).

Повідомлення не оголошується: `@[Error.Required]` + `title` поля.

### `total` — сума колонки колекції

Список імен, як і `required`, але оголошується **тільки на колекції**: на записі падає — `total: declared on …, which is a record. A sum is a member of a collection`. Кожне ім'я дає властивість на типі **масиву**:

```js
'TRowArray.Sum'() { return this.$sum(c => c.Sum); }
```

Тобто підсумок рахує клієнт по завантажених рядках, а не SQL. 🟡 Форма його поки не малює: рядка підсумків у білдері XAML немає взагалі ([forms.md](forms.md) → «Відкрите»).

### `when` — умова над правилами

Умова майже ніколи не стосується одного поля: «в кредит» додає і `DueDate`, і `CreditDays`; «роздріб» міняє й обов'язковість, і видимість. Тому умова — **область дії над правилами**, а не параметр правила:

```jsonc
"rules": {
  "required": ["StoreTo", "Agent"],
  "when": [
    { "test": "this.PaymentType === 'credit'", "required": ["DueDate", "CreditDays"] }
  ]
}
```

Усередині `when` — ті самі види в тих самих формах. **Глибина рівно 1**: `when` усередині `when` заборонений, як і вкладений `body` у формах ([forms.md](forms.md)).

Правила зі `when` **додаються** до безумовних, а не заміщують їх: це різні оголошення. Шарування — 🟡 документ, що написав свій `when`, заміщує список кореня цілком; це відкладення, а не рішення («Як зливаються шари»).

### `visible`

Значення **і є** вираз — окремої охорони немає й бути не може: умова над умовою.

Статичного `visible: false` немає: приховати безумовно = прибрати поле зі складу форми.

### `inherit` — значення по посиланню

Поле-отримувач бере значення з рядка, на який вказує сусіднє `Ref`-поле, і **далі значення належить запису**.

```jsonc
"inherit": { "Unit": { "ref": "Item", "field": "Unit" } }
```

**Це денормалізація з правом на розбіжність, а не похідне значення.** Похідне (властивість, JOIN) завжди дорівнює джерелу. Успадковане дорівнює джерелу **в момент вибору** і далі від нього від'єднане: документ пам'ятає, в чому відвантажували, навіть якщо базову одиницю товару потім змінили. Тому це справжня колонка, і тому `inherit` разом із властивістю на одному полі — помилка: там значенням володіє get, тут — запис.

**Момент — беззастережний перезапис.** Зміна `Ref`-поля завжди перезаписує успадковане: *обрав товар — отримав його реквізити*. Умовний варіант нема на чому побудувати — обробник зміни отримує нове значення й більше нічого, розрізнення «користувач обрав» проти «проставилось програмно» в ньому не виражається. Опції «заповнити лише якщо порожньо» немає свідомо: вона робить поведінку залежною від історії поля.

**Один хоп.** `{ ref, field }` структурно не вміє ланцюга: `VatRate ← Item.Group.VatRate` не виражається. Потрібен другий хоп — матеріалізуй проміжне поле в `Item` тим самим механізмом.

**Область імен.** `ref` резолвиться в **тому самому** наборі полів, що й отримувач: поле рядка — серед полів своєї колекції, поле шапки — серед `fields` власника таблиці.

**Ключ стоїть на отримувачі, не на джерелі.** Альтернатива (`"Item": { "brings": [...] }`) відкинута: при записі на отримувачі інваріант «у поля рівно одне джерело значення» тримає структура — два різних `Ref` не можуть претендувати на одне `Unit`, бо ключ у мапі один. Ціна — при трьох реквізитах від одного товару `"ref": "Item"` повториться тричі; це дешевше за перехресну перевірку.

**Скорочення немає.** `{ "ref": "Item" }` із `field` за замовчуванням з імені отримувача не приймається — це друге прочитання однієї позиції заради дев'яти символів.

**Що генерується — Map як оголошення типу.** Щоб успадкування спрацювало, обраний об'єкт мусить донести поле-джерело. Позначки для цього немає і не буде: склад Map — транзитивне замикання по деклараціях. Місце — Map **документа**, а не вибірка, що годує пікер: слот мусить існувати в типі, інакше присвоєння з пікера обріже об'єкт по відомих властивостях і значення зникне ще до обробника зміни. Замикання рахується над **типами** — генератор додає оголошення колонки, а не JOIN; вартість на шляху завантаження нульова.

**`inherit` не скасовує `required`.** Джерело може не спрацювати — поки не обрано `Item`, успадковане поле порожнє.

## Правила по видах рядків

Коли колекція оголосила `kinds`, рядки кожного виду приїжджають окремою колекцією зі складеним іменем ([metadata.md](metadata.md) → «`kinds` — види рядків»). Звідси **різні шляхи**: `Document.StockRows[].Item` і `Document.ServiceRows[].Item` — різні адреси того самого стовпця тієї самої таблиці.

```jsonc
"kinds": {
  "Stock":   { "properties": { "Sum": { "get": "this.Qty * this.Price" } },
               "rules": { "required": ["Item", "Qty", "Price"] } },
  "Service": { "rules": { "required": ["Description", "Sum"] } }
}
```

Оголошення приземляються двома різними способами, і по видах рядків розводяться обидва:

| Що | Чим ключується приземлення | Адреса при видах |
|---|---|---|
| `required` | шляхом (`validators`) | `Document.StockRows[].Item` |
| `inherit` | шляхом (`events`) | те саме |
| `properties` | **типом** (`properties` шаблону) | `TStockRow.Sum` |
| `visible` | **типом** | те саме; 🟡 генератора ще немає |

Один тип на всі види означав би, що `TRow.Sum` визначається рівно раз, — і тоді властивість, різна по видах, не виражалася б узагалі. **Тому тип на вид зроблено в завантаженні, до всіх правил:** N рекордсетів замість одного, кожен зі своїм фільтром по дискримінатору. Разом із цим зник трюк з умовним `ParentId`, яким один рекордсет розводився по N колекціях, — він існував рівно для того, щоб не заводити другий тип.

**Приклад вище показує, чому це не оптимізація.** У `Stock` `Sum` — обчислюване, у `Service` — вводиться. Це не «два різних вирази», а різна **природа** поля: там геттер, тут дані. Одним типом невиразне в принципі, жодним порядком генерації не обходиться.

**Порожній вид — не порожній шар.** Вид, що не написав нічого, отримує правила колекції без змін; вид, що написав, кладе своє поверх за тим самим законом, що документ кладе поверх кореня («Як зливаються шари»). Один закон, дві осі, одна реалізація.

## Вирази

JS, повна форма з `this.`:

```jsonc
"properties": { "Sum": { "get": "this.Qty * this.Price" } }
```

**`this.` не косметика.** Воно розводить ім'я поля і JS-глобал: у документа baseline-поле `Date`, і голе `Date` було б неоднозначним. Другий наслідок — усередині лямбди (`r => r.Sum`) локальні імена не `this`-кореневі, тому не плутаються з полями, і аналіз скоупів не потрібен.

Вкладеність у виразі вільна. Проміжне ім'я заводиться тоді, коли значення потрібне двічі або показується у формі, — а не тому, що вираз не вміщується.

Область імен: **`fields` ∪ baseline ∪ `$`-імена `properties`** своєї області. У блоці виду колонки ті самі, що в колекції: власних полів вид не має — таблиця одна, склад колонок один на всі види; `$`-імена — колекції плюс свої.

### Перевірка — Jint 🚧

Прийнята форма: валідація парсить вираз (Jint / Esprima) і обходить AST. Сьогодні цього немає ніде — `Jint` у шарі метаданих не підключений, і `a2 meta validate` ([validate.md](validate.md)) виразів не читає:

- синтаксис;
- кожне `this.X` резолвиться у своїй області; dangling — помилка;
- звернення до полів цілі (`this.Item.Unit`) резолвиться в endpoint із `target` поля `Item`;
- методи над колекціями (`$sum`, …) — за реєстром платформи;
- граф залежностей будується за входженнями `this.X`; **цикл — помилка збірки**.

Це і є те, заради чого вираз лишається рядком, а не структурою: пастка стоїть у валідаторі, до деплою, і опечатка не доїжджає до браузера.

## `properties` — властивості моделі (version >= 8668)

Блок-сусід `fields` і `rules` у своїй області. Ключ — ім'я властивості, значення — `{ get }` або `{ get, set }`: JS, як `{ get, set }` у `properties` шаблону A2v10 і `computed` у Vue. `fields` — data моделі, `properties` — її computed, `rules` — валідатори й події: формат повторює реактивну модель платформи.

```jsonc
"fields": {
  "Qty":   { "type": "qty" },
  "Price": { "type": "price" },
  "Sum":   { "type": "amount" }
},
"properties": {
  "Sum":   { "get": "this.Qty * this.Price", "set": "this.Qty = value / this.Price" },
  "$Base": { "type": "amount", "get": "this.Qty * this.Price" }
}
```

Ключ двох родів, і різниця — закон платформи, а не синтаксис: **при збереженні на сервер їде все, що не починається з `$`**, незалежно від того, як значення отримано.

| Ключ | Що це | `type` | Збереження |
|---|---|---|---|
| поле з `fields` / baseline | властивість стоїть над колонкою; у колонку їде те, що повернув get | заборонений — тип у `fields` | їде, як будь-яке поле |
| `$Ім'я` | власне ім'я без колонки | обов'язковий — форма бере з домену формат, ширину й контрол | не їде ніколи |

- **Форма значення одна — об'єкт.** Рядка-скорочення немає: `{ "get": "…" }` — властивість лише для читання, `{ "get": "…", "set": "…" }` — з вводом.
- **`get` — вираз; `set` — JS-оператор над `value`**, тим, що ввів користувач. set пише в поля свого запису: `"this.Qty = value / this.Price"`.
- **Домени `$`-імені — лише скалярні** (`amount`, `qty`, `percent`, `date`, `string`, `boolean`). Посилання не проходить: значення на клієнті — об'єкт моделі, а не Id, а рендер лукапа спирається на Map, якого в імені без колонки немає.
- **Ім'я, тип і вираз з'являються разом.** Розірвати їх на два блоки означало б напівоголошене ім'я — назване, але без значення.
- **Редагованість виводиться, а не оголошується.** Властивість без set форма показує й не дає вводити (як колонку з `sqlAs`); із set — звичайний контрол свого домену. `$`-ім'я форма називає в `fields` вузла, як поле ([forms.md](forms.md)), — лише форма `edit`: властивості живуть у шаблоні картки, список і пікер їх не мають.

**Чому не правило.** У `rules` ключ — вид правила, а ім'я властивості, яку він дає, називає платформа (`visible` → `$DiscountVisible`, `total` → `TRowArray.Sum`). Тут ім'я називає автор. Колишній `rules.computed` (над колонкою) і `derived` (`$`-ім'я) були одним поняттям, розірваним інверсією ключа: у формі `computed: { Поле: "вираз" }` не було місця для `type`, тому `$`-імена виселили в окремий блок. Обидва замінено цим.

### Як поле отримує значення

Значення поля виробляють чотири різні механізми, і кожен названий тим, **як** значення виникає:

| Як поле отримує значення | Що | Коли |
|---|---|---|
| нуль домену | тип поля (`0` / `false`, решта `NULL`) | створення |
| при створенні запису | `initialValues` | Load |
| знімок при виборі посилання | `inherit` | зміна `Ref` |
| завжди дорівнює виразу | `properties` (get) | постійно |

Знімок (`inherit`) від'єднується від джерела; властивість від нього не відрізняється ніколи. Тому `inherit` і властивість на одному полі — помилка: одне поле, одне джерело значення.

**Колекція у виразі називається так, як вона приїхала.** `this.Rows` існує, лише поки колекція **не** оголосила `kinds`; оголосила — у моделі є `this.StockRows` і `this.ServiceRows`, а `Rows` немає, і підсумок документа пишеться перерахуванням: `this.StockRows.Sum + this.ServiceRows.Sum`.

Wildcard'а по видах немає, і це те саме рішення, що в `each` ([metadata.md](metadata.md) → «`each` — по чому ітеруємо»): доданий згодом вид мовчки поїхав би в підсумок. Обидві сторони тихі — або новий вид не порахували, або порахували несумісні величини, — і обрана та, що не псує вже правильне число. Ціна: доданий вид, якого не дописали в підсумок, нічим не видно.

Колонку, яку обчислює БД, оголошує інше слово — `sqlAs` у `fields` ([metadata.md](metadata.md) → ключі поля). Два шари — два слова: властивість — клієнтська модель над колонкою, яку пише збереження; `sqlAs` називає мову, і JS-вираз за аналогією туди не потрапляє. Вони можуть жити на одному полі; узгодженість виразів — на авторі.

### Шари й місце

- **Шаруються по ключу**, як мапи `rules`, на обох осях: документ над `storage` перекриває властивість кореня, вид рядка — властивість колекції (`kinds.<Kind>.properties`).
- **Документ над `storage` оголошує свої вільно.** Властивість — не сховище, тож правило «документ над `storage` не повторює структуру» її не стосується; кожен документ — свій шаблон і свої типи. `$Margin` у `waybillout` інші документи над тією самою таблицею не бачать.
- **Ослаблення не пишеться.** Прибрати властивість кореня документ не може: якщо `Sum` обчислюється не в усіх документах, властивість переноситься вниз, у ті, де обчислюється.
- **Вид рядка — свій тип.** `Sum` — get у `Stock` і дані в `Service`: одним типом невиразне, тип на вид це дає (розділ «Правила по видах рядків»).
- 🚧 **Файл операції** (`<op>.operation.json`) `properties` відхиляє. Тип один на всі операції документа, тож властивість однієї операції — тест по `this.Operation` у get, а генератора такого тесту немає.

### Лінза — властивість із set

Властивість із set — лінза: **get** показує значення, **set** розкладає введене назад у первинні поля. Де вона стоїть, вирішує одне питання — чи має показане значення **фіксований смисл**:

| Смисл показаного | Де | Приклад |
|---|---|---|
| фіксований | над колонкою, зберігається | `Sum = Qty × Price`; ввів суму — set рахує `Qty` (ціна задана, комплектація) або `Price` |
| залежить від режиму | лише `$`-ім'я | ціна з ПДВ чи без за `VatIncluded`: над `Price` збереглася б ціна з ПДВ, і фіксований смисл колонки зламався б мовчки |

- **Трикутник `Qty × Price = Sum`** — частий випадок без ПДВ, і що рухати при вводі третього кута, вирішує автор: `"set": "this.Qty = value / this.Price"` чи `"set": "this.Price = value / this.Qty"`.
- **Закони лінзи.** PutGet: set, потім get повертає введене — ввів 100, бачиш 100. GetPut: set того, що показав get, даних не змінює. Округлення порушує PutGet у межах допуску: ціна з 6 знаками, сума до копійки.
- **Програмний запис іде повз set.** set викликає лише ввід у контрол; народження, `inherit`, завантаження пишуть первинні поля напряму й нічого не перераховують.

🟡 ПДВ — не авторська лінза: формулу й обернену до неї (виділення ПДВ із ціни, утримання числа на екрані при зміні `VatIncluded`) несе правило `vat`, дизайн — `concepts/vat` у репозиторії скіла, у нормі ще немає.

## Чого в `rules` немає

- **Перевірок значення** (`min` / `max` / `regex` / `unique` / довжина) — вони **виводяться з фактів у `fields`**, а не оголошуються правилом: `length` уже сьогодні приземляється і в `nvarchar(N)`, і в `maxlength` контрола, `unique` — і в індекс, і в async-перевірку дубля, регулярка пошти — з домену `Email` (🚧). Перевірка не є одиницею оголошення; одиниця — факт, з якого вона випливає ([metadata.md](metadata.md) → «Що НЕ пишеться у field»).
- **`readonly`** — runtime-прапор запиту, приходить із кожною відповіддю; build-time факту тут немає ([forms.md](forms.md) → «`readonly`»).
- **другої мови для умов** — умова це той самий JS, що й вираз.
- **умов по виду рядка** — поле-дискримінатор у модель не їде, тому `this.Kind` не існує й тест по ньому написати нічим. Вид задається позицією блоку (`kinds.<Kind>.rules`). Двох написань одного факту тут немає за побудовою, а не за забороною — і це важливо: `when` із помилкою в імені виду дав би мертве правило мовчки, ключ мапи падає об оголошений набір.
- **`$`-імен у серверних позиціях**: `post`, `initialValues`, `inherit` (як отримувач), `lookup`, `presentation`, `displayAs`, виміри й ресурси журналу. Причина одна — значення не доїжджає до сервера.
- **`requiredMessage`** — див. `required`.

## Валідація

- імена полів резолвляться у `fields` / baseline / `$`-імена `properties` своєї області; dangling — помилка;
- `required` не приймає `$`-імен: обчислюване поле завжди має значення, перевіряти нема чого;
- невідомий вид правила — помилка з переліком наявних (`available`), а не «unknown property»;
- `when`: `test` обов'язковий; вкладений `when` — помилка;
- `inherit`: `ref` існує у своїй області й має `type: "ref"`; `field` існує в endpoint-і з `ref.target`; тип сумісний (для `Ref` збігається й `target`);
- `properties` (version >= 8668), при завантаженні: `get` обов'язковий; ключ без `$` — поле своєї області, без `type`; `$`-ключ — з `type`, домен не посилання; властивість на полі з `inherit` — помилка; `properties` у файлі операції — помилка;
- ключ усередині `kinds` резолвиться в оголошений набір видів; невідоме ім'я — помилка з переліком (`available`);
- `this.<Collection>` у виразі резолвиться в **те, що приїхало**: для колекції з `kinds` це імена видів, і `this.Rows` там dangling;
- 🟡 склад ключів (`additionalProperties: false`) триматиме JSON Schema — **її ще немає**. Сьогодні незнайомий ключ не відхиляє ніхто: завантажувач мовчки його викидає.

## Що генерується

```typescript
properties: {
    'TRow.$Base'(this: TRow)  { return this.Qty * this.Price; },
    'TRow.Sum'(this: TRow)    { return this.$Base * (1 - this.Discount); },
    'TRow.Qty': { get(this: TRow) { return this.Units * this.Ratio; },
                  set(this: TRow, value: any) { this.Units = value / this.Ratio; } },
    'TRow.$DiscountVisible'(this: TRow) { return this.Qty > 10; }
},
validators: {
    'Document.StoreTo': "@[Error.Required]",
    'Document.DueDate': { valid: "@[Error.Required]",
                          applyIf: d => d.PaymentType === 'credit' }
},
events: {
    'Document.Rows[].Item.change'(this: TRoot, row: TRow) { /* Unit ← Item */ }
}
```

Коли колекція оголосила `kinds`, шлях несе складене ім'я — `'Document.StockRows[].Item'`, `'Document.ServiceRows[].Item'`, — а тип запису теж свій на вид (`TStockRow`). Правило, оголошене на колекції, роздається в кожен вид; оголошене у виді — тільки у свій.

`applyIf` — функція `(elem, value) => boolean`, `elem` — запис, що несе поле; `false` пропускає правило (платформа: `validateImpl` у `main.js`, тип `templateValidatorObj` у `platform.d.ts`).

## Відкрите

1. 🟡 **Серверне виконання.** Jint уміє не лише парсити, а й виконувати. Тоді get властивостей і `required` отримують серверну сторону, і закривається наявна дірка: документ, що приїхав через API або імпорт, форми не бачив — обчислювану колонку `Sum` не порахував ніхто. Умова — host-об'єкт у Jint мусить віддавати `this` з тими самими іменами, тобто поверхня виразу = перетин того, що є в браузерній моделі і в host-і.
2. 🟡 **Реєстр поверхні.** Список того, що легальне у виразі понад `this.<поле>`: методи колекцій (`$sum`, …), `$root` / `$parent`, утиліти. Потрібен валідатору, не автору.
3. 🟡 **Імена всередині лямбди.** `r => r.Sum` сьогодні не перевіряється — потрібен вивід типу параметра з колекції.
4. 🟡 **Умова через межу області.** `when` у правилах рядка бачить поля рядка. Реальний випадок — залежність від поля шапки; кандидат `this.$parent` / `$root`, але для серверного виконання потрібне підтвердження, що воно є й там. Той самий вимір, що в `inherit` (успадкування рядком із шапки).
5. 🟡 **Реєстр системних `$`-імен платформи.** `$` — простір імен рантайму; авторське ім'я, що збіглося з платформним, затінить його **тихо**. Потрібна звірка валідатором зі списком платформи (або розділ: один `$` — автору, `$$` — платформі).
6. 🟡 **Уточнення домену в `fields`** (`min` / `max` / `pattern` як сусіди `length`) — форма не описана. Наслідок відомий і неприємний: таке уточнення приземляється в CHECK, а додавання CHECK до заповненої таблиці — посилення обмеження, тобто ручна міграція у звіті деплою. Це та сама ціна, що в зміні `type` наявної колонки на домен із нулем, і приймати її треба свідомо.
