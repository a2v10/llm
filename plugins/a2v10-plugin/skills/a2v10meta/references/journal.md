# Journal — metadata-driven

## Призначення

Журнал — регістр накопичення. Пишеться **виключно через `post[]`** документів, не через власний UI. Користувач не редагує журнал напряму. (`post[]` живе у файлі операції або самодостатнього документа — залежно від варіанта розкладки, `references/metadata.md` → «`document` — один шар або два»; для журналу різниці немає.)

## metadata.json журналу

```jsonc
// journal/stock/metadata.json
{
  "table": "StockJournal",
  "fields": {
    "InOut":     { "type": "direction" },
    "Document":  { "type": "document", "target": "/document" },
    "Operation": { "type": "operation" },
    "Detail":    { "type": "row" },
    "Store":     { "type": "ref", "target": "/catalog/store" },
    "Item":      { "type": "ref", "target": "/catalog/item" },
    "Qty":       { "type": "qty" },
    "Sum":       { "type": "amount" }
  }
}
```

| Секція | Призначення |
|---|---|
| `fields` | **усі** колонки журналу — і розрізи, і показники; той самий field-shape, що в catalog |
| `checks` | Прив'язка SQL-перевірок до post/unpost операцій-писарів: `{ onPost: [...], onUnPost: [...] }` — див. нижче |

Окремих секцій під «виміри» і «показники» тут **немає**: розріз від показника відрізняє домен поля, а не секція. (`dimensions`/`measures` — словник **марта**, іншого шару: журнал каже, як факти лежать, март — як їх питають.)

**Baseline** (генератор додає сам, у `fields` не пишуться):

| Поле | Тип | Призначення |
|---|---|---|
| `Id` | identity | PK |
| `Date` | `date` | Дата операції (копія з документа — для швидких діапазонних запитів) |

**Колонки, які читає платформа, оголошує автор** — вона знаходить їх **за типом**, тому ім'я обирає автор (та сама фігура, що `Autonum` чи `RowKind`; [metadata.md](metadata.md) → «Types» → «Семантичні домени»):

| Тип | Що це |
|---|---|
| `Direction` | знак плеча: `+1` / `-1`. Словник (`In`/`Out`, Дт/Кт) — презентація, у колонці лише знак |
| `Document` | recorder: документ-джерело. Тримає ідемпотентність unpost (`DELETE WHERE Document = @Id`) |
| `Operation` | операція документа-джерела — денормалізація, щоб звіт не JOIN-ив `doc.Documents` |
| `Row` | Id проведеного рядка-джерела; `null`, коли в `post` немає `each` |

**Колонки й nullability.** Nullable **усі**, окрім `Id`: `NOT NULL` не отримує ніщо, ні розріз, ні показник. Тому колонка, яку post не заповнив, ляже `NULL`, і СУБД цього не зловить — розріджені колонки тут штатна форма, а не дефект: одна таблиця несе аналітику всіх своїх писарів.

Що **не пишеться** в metadata журналу: `post`, `traits`.

## Як документ пише в журнал

Через блок `post[]` в `document/<op>/metadata.json`. Детально — `references/metadata.md` розділ «post».

Мінімальний приклад (stock, рядки):

```jsonc
// document/waybillin/metadata.json
{
  "post": [
    {
      "journal":  "/journal/stock",
      "dir":      "in",
      "each":     { "details": "Rows" },
      "document": { "Store": "StoreTo" }
    }
  ]
}
```

- `dir: "in"` → `InOut = +1`; `dir: "out"` → `InOut = -1`
- `each` — `{ details, kinds }`: одна колекція і деякі її види; відсутній → один запис на документ ([metadata.md](metadata.md) → «`each` — по чому ітеруємо»)
- `document` / `row` — тільки відхилення від auto-mapping; значення завжди голе ім'я поля з відповідного набору
- `Document`, `Date` — baseline журналу, заповнює платформа; в override-блоках не пишуться

## `checks` — серверні перевірки проведення

```jsonc
// journal/stock/metadata.json
"checks": {
  "onPost":   ["jrn.CheckStockPost"],
  "onUnPost": ["jrn.CheckStockUnPost"]
}
```

**Що це.** Прив'язка рукописних SQL-процедур до згенерованого post/unpost **кожної** операції, що пише в цей журнал. Тіло перевірки — завжди матеріалізований SQL (звичайна процедура); metadata декларує тільки виклик. Континуум у дії: прив'язка — декларація, тіло — код.

**Чому на журналі, а не на операції.** Інваріант належить стрічці журналу, а не тим, хто в неї пише. Операція з `post[]` у журнал отримує його перевірки автоматично — нова операція **не може забути** виклик. Ручна розводка викликів по шляхах проведення — реальний клас виробничих багів («у одному з шести шляхів виклику немає»); декларація на журналі виключає його структурно, зберігаючи відкритий світ post.

**Порядок — контракт генератора:** гард → транзакція → **checks** → мутації → `Done` (повна схема — `metadata.md` → post → «Post/unpost»). Перевірка бачить світ **до** мутацій цього виклику: на post — документ збережено, його проводок ще немає; на unpost — проводки документа ще в журналі (його слід читається `WHERE Document = @Id`). `throw` з перевірки відкочує транзакцію цілком.

**Чому НЕ constraint-DSL.** Реальні інваріанти («залишок не може бути від'ємним») — це дисципліна переходів, не предикат над станом: перевірка кількості коректна лише під гарантією append-only позиції, кроки взаємозалежні, потрібні фазний прокат по живій базі та якісні повідомлення з адресами проблем. Декларативний вираз рівня `balance >= 0` для такого **некоректний**, не просто бідний. Загальне, чесно виведене з частного, — гарантія виклику, не мова предикатів. Повертатися до декларативної форми — тільки якщо 3+ матеріалізовані check-и покажуть спільний shape (загальне з частного, не навпаки).

**Критерій «однієї фрази».** Правило, яке не формулюється одною фразою користувачу («з партією працюєш тільки від її останнього руху», «не можна списати більше, ніж є») — взагалі не кандидат у декларативний шар; його місце в SQL за `checks`. Складність правила оплачується не розробником один раз, а кожним користувачем щодня.

**Режим log/throw — не metadata.** Слот у policy-реєстрі (організаційна настройка): перевірка сама вирішує кидати чи писати в лог. Це дає штатний фазний прокат (log → чистка історії → throw) без зміни metadata, а log-режим лишається назавжди як health-скан по історії.

## Auto-mapping

Поле журналу резолвиться за **іменем і доменом**: шукається поле документа з тим самим іменем і сумісним доменом (домен + `target`, не SQL-тип). Збіглося — override не потрібен.

| Поле журналу | Auto-резолюція |
|---|---|
| `Date` (baseline), `Document` / `Row` (за типом) | Заповнює платформа |
| `Operation` | Як звичайне поле — з однойменного поля документа (`Operation` storage родини) |
| `X` — рівно один кандидат у шапці або в рядку | Резолвиться |
| `X` — кандидати і в шапці, і в рядку | Помилка; знімається вказівкою в `document` або `row` |
| `X` — ім'я є, домен не той | Помилка |

Домен фільтрує кандидатів, але не зіставляє: без збігу імені резолюції немає. Тільки відхилення від цих правил потрапляють у блоки `document` / `row`.

## Validation 🚧

Валідатор перевіряє `post[]` при `a2 validate` ([validate.md](validate.md) — команди ще немає):
- Ключі `document` / `row` резолвуються у `fields` журналу
- Значення `document` — у `fields`/baseline документа; значення `row` — у `fields` колекції `each.details`
- `row` без `each` — помилка
- Одне поле журналу в обох блоках — помилка
- `each.kinds` — непорожній тоді і тільки тоді, коли колекція оголосила види
- Невідоме ім'я → `available` у відповіді

## UI журналу

Auto з `fields`: колонки потрапляють у `index.columns`. Override через `forms.index` за потребою (та сама схема, що і в catalog).

## Приклад — stock journal

```jsonc
// journal/stock/metadata.json
{
  "description": "Рух товарів по складах",
  "table": "StockJournal",
  "fields": {
    "InOut":     { "type": "direction" },
    "Document":  { "type": "document", "target": "/document" },
    "Operation": { "type": "operation" },
    "Detail":    { "type": "row" },
    "Store":     { "type": "ref", "target": "/catalog/store" },
    "Item":      { "type": "ref", "target": "/catalog/item" },
    "Qty":       { "type": "qty" },
    "Sum":       { "type": "amount" }
  }
}
```

Документи що пишуть у цей журнал: `waybillin` (`dir: In`), `waybillout` (`dir: Out`), `waybillmove` (two-leg: `Out` зі StoreFrom + `In` у StoreTo).
