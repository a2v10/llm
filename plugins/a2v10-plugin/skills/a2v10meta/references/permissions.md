# Права доступу

> 🚧 **Файл цілком — у роботі, підсистеми в платформі ще немає.** Норма записана й
> чинна: права з'являться саме такими, і найближчим часом. Сьогодні з описаного не
> працює нічого — ні рядок у таблиці, ні перевірка.
>
> - kind `roles` платформа не резолвить ([kinds.md](kinds.md));
> - ключ `grants` не читає жоден генератор, а схема endpoint-у його **відхиляє**
>   (`additionalProperties: false`) — рідкий випадок, коли 🚧 ловиться машиною, а не
>   дисципліною;
> - таблиці `Grants` немає ніде: ні DDL, ні наповнення деплоєм, ні join-у в
>   згенерованому SQL;
> - `useGrants` в `app.json` не читає ніхто (сам файл читається — заради `platformid`);
> - `menu.json` по правах не фільтрується — шелл і aux читають його двома різними
>   місцями, обидва цілком;
> - своєї security-схеми немає, є тільки legacy у `@sql/legacy/`.
>
> **Що вже є:** `PermissionFlag` у платформі — шість дієслів плюс три вільні біти.
> Єдина частина цього файла, під якою вже лежить код; на тих вільних бітах тримається
> «Відкинуте» про `all`.
>
> **Отже:** `grants` не писати, теку `roles/` не заводити, прав авторові не обіцяти.
> Застосунок сьогодні пишеться без них, а на «обмежити доступ» відповідь одна —
> платформа цього ще не виконує.

Права оголошуються **один раз — на endpoint-і**. Меню їх не оголошує, а виводить: що юзеру видно, вирішує те саме `CanView`. Безпеки меню не тримає в жодному разі — дозвіл стоїть у згенерованому SQL, і пункт, якого в меню немає, однаково досяжний за URL і лукапом.

## Роль — kind `roles`

Закритий словник застосунку, за зразком `autonum`: один файл, мапа по ключу, свого екрана і адреси немає (тому й у меню не потрапляє — [menu.md](menu.md)).

```jsonc
// roles/metadata.json
{
  "roles": {
    "accountant":  { "name": "Бухгалтер" },
    "storekeeper": { "name": "Комірник" }
  }
}
```

Матеріалізується не у свою таблицю, а в таблицю ролей security-схеми — тієї, якої ще немає (врізка вгорі; на колонках legacy-схеми будувати не можна). Вимога до майбутньої з нашого боку одна: **ключ-рядок є natural key**, відображуване ім'я лежить окремо, сурогатний `Id` у metadata не з'являється ніколи.

**Ключ і є ідентичність.** Перейменування як операції не існує: інший ключ — інша роль. Деплой робить upsert по ключу, бо на роль посилається членство.

`admin` — **зарезервований**: роль predefined, не оголошується, і оголошення з таким ключем відхиляється на збірці. Причина не в зручності: `Grants` заповнює деплой, а лагодити зламаний деплой має адмін — його права не можуть лежати в тому, що він лагодить.

**Членство юзерів у ролях — дані БД**, не декларація: список юзерів під час проектування невідомий. Ролей у юзера кілька, вони **об'єднуються**; `deny` немає ніде.

## Об'єкт права — endpoint

Рядок у `Grants` має рівно той, хто має адресу. Наслідки, які не потребують окремого механізму:

- операція документа (`document/waybillin`) — окремий endpoint, тому права по операціях виходять даром; база родини адреси не має і рядка не отримує;
- `enum`, `autonum`, `roles` — екрана немає, прав немає;
- друкована форма прав не має ([print.md](print.md)) — вона не endpoint.

**Права не поширюються через посилання.** `Ref`-поле показує `Name` з довідника, на який прав немає, і це не діра: вимога прав на ціль ламала б кожен документ. Вузол замкнутий — право стоїть на вході, не на даних, до яких можна дотягнутись із замикання.

## Дієслова

Набір закритий, збігається з `PermissionFlag` платформи:

| Дієслово | Колонка `Grants` | Де осмислене |
|---|---|---|
| view | `CanView` | скрізь, де є адреса |
| create / edit / delete | `CanCreate` / `CanEdit` / `CanDelete` | catalog, операція документа |
| apply / unapply | `CanApply` / `CanUnapply` | операція документа з `post` |

Дієслово, неосмислене для kind-у (`edit` на звіті, `apply` на довіднику), — **помилка збірки**, не мовчазний нуль.

## `grants` — де оголошуються права

У файлі endpoint-у, ключем `grants`: **роль → перелік дієслів**.

```jsonc
// catalog/agent/metadata.json
{
  "table": "Agents",
  "grants": {
    "accountant": ["view", "create", "edit", "delete"],
    "manager":    ["view"]
  }
}
```

```jsonc
// document/waybillin/metadata.json
{
  "storage": "document",
  "grants": {
    "storekeeper": ["view", "create", "edit", "apply"],
    "accountant":  ["view", "apply", "unapply"]
  }
}
```

- **Ключ — роль, а не дієслово.** Транспонований вигляд (`"view": [...]`) читається як «хто може дивитись», але роль тоді розмазана по шести рядках, а правлять зазвичай роль цілком.
- **Ім'я те саме, що в таблиці, куди це лягає** — одне поняття по обидва боки деплою.
- `grants` **не шарується** зі storage на операції: рядок таблиці належить операції, і якщо блок може приїхати з двох файлів, права endpoint-у більше не читаються по одному файлу. `post` теж не шарується.
- Роль, якої немає у словнику, — помилка збірки.
- `admin` тут не пишуть ніколи: він і так проходить усе.

**При `useGrants: true` ключ обов'язковий у кожного адресованого endpoint-у.** «Нікому, крім адміна» пишеться явним `"grants": {}`. Причина — не строгість: пропущений ключ і свідома порожнеча інакше виглядають однаково (endpoint зник), а зникнення має пояснюватись рядком у файлі, не його відсутністю.

## `app.json` — вмикач

Права вмикаються на застосунок цілком, у `MainApp/app.json`:

```jsonc
{
  "platformid": "bigint",
  "useGrants": true
}
```

`useGrants: false` (або ключ відсутній) — підсистеми немає: `Grants` не заповнюється, перевірок немає, оголошені `grants`-блоки лежать без дії. Це і є шлях міграції: розмітити застосунок цілком, подивитись, і ввімкнути одним рядком.

Умовчання «все дозволено» не існує ніде: словник збудований з `Can*` без `Deny*`, тому відсутність рядка читається рівно одним способом. Увімкнено і жодного гранту — працює тільки адмін; це та сама точка відновлення, заради якої він predefined.

## Матеріалізація: таблиця `Grants`

Гранти оголошені в metadata, тобто **design-time**: адмін їх не редагує, зміна прав — правка файла і деплой. Деплой розкладає їх у плоску таблицю:

| Endpoint | Role | CanView | CanEdit | CanDelete | CanCreate | CanApply | CanUnapply |
|---|---|---|---|---|---|---|---|
| `catalog/agent` | `accountant` | 1 | 1 | 0 | 1 | 0 | 0 |

**Окремі бітові колонки, не упакована маска**: об'єднання ролей юзера — це `max()` по колонці, а агрегату побітового OR у SQL Server немає.

**Політика деплою в цих двох таблиць різна, і це випливає зі ссилок:**

| Таблиця | На неї посилаються | Деплой |
|---|---|---|
| `Grants` | ніхто — вона похідна | перезапис цілком, delete + insert |
| ролі | членство юзерів | upsert по ключу |

## Перевірка — всередині SQL

Перевірка живе в згенерованому SQL, не на беку: фільтр по рядках (компанія, юзер) в SQL обов'язковий у будь-якому разі, і тримати два рівні прав у двох різних шарах немає причини. Ефективні права юзера — `join` з `Grants` по його ролях із `max()` по колонках.

Три речі, які тут ламаються тихо, якщо їх не тримати:

1. **Гейт — не фільтр.** Рівень endpoint-у — `throw`. Умовою в `where` відмова перетворюється на порожнечу: список показує «немає записів» замість «немає доступу», а `update`/`delete` зачіпає 0 рядків і **рапортує успіх**. `where` лишається тільки рівню рядків.
2. **Перевірка — у тексті процедури, а не навколо нього.** Якщо її підмішує білдер у рантаймі, `eject` ([materialize.md](materialize.md)) винесе текст у файл, а обгортка лишиться в генераторі — матеріалізація мовчки зніме захист. Матеріалізація в нас континуум, а не крайній випадок.
3. **Адмін — одне коротке замикання на початку**, до гейта і до фільтра: адміну можна все.

**Кешу прав на беку немає.** Таблиця дрібна і гаряча, її кешує сам движок; кеш на беку довелося б інвалідувати на двох незалежних подіях (деплой переписав `Grants`, адмін змінив членство). Наслідок, який варто знати: зміна ролі діє з наступного запиту, без перелогіну.

Прапорці для тулбара (сховати «Провести» тому, в кого немає `apply`) їдуть **системними колонками тієї самої відповіді** — тією ж дорогою, що й `[!!ReadOnly]` ([forms.md](forms.md)). Окремого транспорту немає.

## Меню виводиться з прав

**Ключа `roles` у меню немає.** У листа є `url`, тобто endpoint, тобто рядок у `Grants` — писати те саме вдруге нема чого. Розділ свого права не має і не потребує: він видимий рівно доти, доки в ньому лишається що показати.

| Вузол | Видно, коли |
|---|---|
| у ролях юзера є `admin` | все; фільтр не працює взагалі |
| лист (`url`) | `CanView` на його endpoint-і |
| розділ, підрозділ, aux | лишилась хоч одна видима дитина |
| розпірка (`grow`) | завжди — це декорація, не вузол |

Дані — той самий `group by Endpoint` із `max(CanView)` по ролях юзера, один запит на завантаження шелла. Фільтрувати доводиться у **двох місцях**: шелл і aux читають `menu.json` різним кодом ([menu.md](menu.md)).

**Показати менше, ніж дозволено, — не окрема конструкція**: пункт просто не пишуть у `menu.json`. Endpoint лишається досяжним за URL і лукапом, і це вже сказано в `menu.md`. Ключ під «дозволено, але не показувати» не заводити, доки не з'явиться випадок, якого цим не покрити.

## Відкинуте (не повертатися)

- **`all` як скорочення грантів** — набір, який воно називає, змінюється з появою нового дієслова, і змінюється в бік **більшого** доступу (у платформі три вільні біти). Мовчазна зміна прав має бути закриваючою. Перелік із 3–6 дієслів дешевший.
- **`deny`** — при об'єднанні ролей заперечення або нічого не значить, або робить результат залежним від порядку. Воно потрібне лише проти wildcard-гранту, а wildcard-гранту немає: не дав = заборонив.
- **Права на поле** — SQL-проекція і форма стають функцією ролі, модель перестає збиратись один раз. Поле, яке не можна показати ролі, майже завжди живе не на цьому endpoint-і.
- **`roles` на вузлах меню** — другий запис того самого предиката. Відсутність ключа читається двояко: на розділі «видно всім», а на листі всередині закритого розділу — «видно тим, кому видно розділ». Однорідний розділ (а таких більшість) змушує повторювати список на кожному листі. Закритий для оголошення `admin` стає невиразним. І обхід дерева знизу вгору при цьому нікуди не дівається — він потрібен, щойно лист може сховатись окремо від розділу.
- **Гранти, редаговані адміном у UI** — вони і є причина реєстру об'єктів прав із сурогатним `Id`, пакування `id:hex` і bag-а на беку. Design-time гранти цього всього не потребують; натомість read-only екран над `Grants` відповідає «що може бухгалтер» у працюючому застосунку.
- **Меню як механізм прав** — сховати пункт не означає заборонити: обхід за URL і лукапом лишається завжди. Меню виводиться з прав, а не навпаки.
- **`acl` як ім'я ключа** — прайор слова тягне те, чого в моделі немає: класичний ACL упорядкований і має `allow`/`deny`, і форма таке приймає (`{"accountant": {"allow": [...], "deny": [...]}}`). `grants` збігається і формою, і семантикою: `GRANT ... TO role` аддитивний і без порядку, а ключі формату — множина іменника по вмісту (`fields`, `forms`, `roles`). `revoke` із того ж прайора не заважає: це операція над станом, а файл станом і є — прибрати право означає прибрати рядок, і ключа під це не існує.

## Відкрите 🟡

- **Розріз по компаніях / рівень рядка** — семантичні колонки `Company` і `User` у генераторі вже є; правило перетину з набором юзера не обговорене. Виражатись воно має типом поля, не виразом.
- **Видалення ролі, яку тримають юзери** — відмова на деплої чи каскад із втратою членства. Напрямок різний, рішення не прийняте.
