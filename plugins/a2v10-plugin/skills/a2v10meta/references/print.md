# print — друковані форми

Бланк: видаткова накладна, акт, рахунок, ТТН. Kind-ом **не є** — власного вікна не має,
з меню не відкривається, викликається завжди зсередини endpoint-а. Тому живе списком у
його `metadata.json`, а не окремою папкою.

## Формула

**Бланк = поверхня × Model × layout.**

| Вісь | Питання | Хто задає |
|---|---|---|
| Поверхня | що взагалі можна дістати | endpoint — замикання по `Ref` |
| Model | що дістаємо для цього бланка | розділ `Model` у файлі бланка |
| Layout | як воно лягає на папір | решта файлу бланка |

Той самий трьохчлен, що у [report.md](report.md), з однією відмінністю: у звіті третій
член обирає користувач у рантаймі, у бланку — автор назавжди. Вибору немає, `defaults`
не потрібні.

## Підключення

Top-level ключ `printForms` у `metadata.json` endpoint-а — **плоский список бланків**, у
порядку меню. Файл бланка не зобов'язаний лежати поруч: він адресується шляхом і може
бути спільним на модуль.

```json
"printForms": [
  { "path": "print/waybill", "title": "@[Print.Waybill]",
    "header": "ПН № {Document.Number} від {Document.Date}" }
]
```

| Ключ | Обов'язковий | Що це |
|---|---|---|
| `path` | так | Шлях файлу бланка від папки endpoint-а, **без розширення** — іменується як view; файл шукається серед `.vxaml`, `.xaml`, `.json` |
| `title` | так | Підпис пункту меню. Локалізується як будь-який підпис (`@[...]`) |
| `header` | ні | Заголовок **вікна**, що містить переглядач, шаблоном над записом |

Інших ключів немає — ні прав, ні умови доступності. Бланк доступний тому, хто відкрив
endpoint.

**Ім'я бланка — останній сегмент `path`**: `print/waybill` відгукується на `waybill`. Ним
адресує URL пункту меню, за ним же бланк знаходиться при відкритті — тому адреса, яку
пише кнопка, і бланк, який резолвиться, розійтися не можуть. Два бланки з одним іменем —
**відмова**, а не «перемагає перший»: URL тоді не адресує жодного з них зокрема.

Розширення не пишеться: інакше `print/waybill.json` і `print/waybill` тихо означали б
один файл, і одне ім'я мало б два написання. Яке розширення стоїть на диску — відповідь
пошуку. Два файли поруч (`waybill.vxaml` і `waybill.json`) — **відмова** з тієї ж причини,
що й два бланки з одним іменем.

`printForms` **не успадковується від `storage`** — на відміну від `initialValues`,
`rules`, `kinds`, `autonum`, `details`, `forms`. Разом із `post` і з тієї ж причини:
бланк — папір під один акт, а дві операції над однією таблицею друкують різні папери.
Storage тримає форму й акту не має — успадковувати там нічого.

### `header` — заголовок вікна, не шапка паперу

Шаблон над записом: `{Document.Number}`, `{Document.Date}`. Кожен шлях починається з
імені моделі й резолвиться по shape **на збірці** — опечатка падає там, як будь-яке інше
ім'я. Шлях іде тільки крізь `Ref`, тому колекції в заголовку немає; саме ім'я моделі без
поля (`{Document}`) — теж помилка.

Значення підставляються у браузері, і дати проходять через форматтер: інтерпольована
`Date` дала б `Fri Aug 28 2026 00:00:00 GMT+0300`.

Не написаний — стоїть `title`.

Шапка самого бланка сюди не входить: її малює ячейка layout-а, а layout скіл не читає.
Це дві осі, збігатися вони не зобов'язані.

### Кнопка `Print`

Непорожній `printForms` **сам** ставить команду `Print` на типові панелі — картки й
списку; кнопка розкривається в меню, по пункту на бланк, у порядку списку. Trait-а
`Print` не існує: список і є відповіддю на питання «чи друкує цей endpoint», так само як
порожній `post` відповідає «чи проводить».

## Файл бланка — два формати, обидва чужі

| Формат | Файл | Коли |
|---|---|---|
| Page | `.vxaml` | потік: текст, таблиця рядків |
| Workbook | `.json` (`{"Workbook": {...}}`) | жорстка сітка ячейок: податкова накладна, ТТН, перенос із 1С |

Вибір — за формою паперу, не за тим, хто пише. Словники обох форматів — у скілі `a2v10`.

Скіл тримає **ребро** endpoint → файл і **`Model`** усередині файлу. Решту вмісту —
розмітку, ячейки, стилі, `Ranges`, шрифти — не читає й не валідує, в обох форматах.

## `Model`

Дерево, ізоморфне моделі, яку отримає рендерер. У Workbook — розділ `"Model"`, у Page —
елемент `<Page.Model>` із тим самим деревом усередині:

```json
"Model": {
  "Document": [
    "No", "Date", "Sum",
    { "Company": ["Name"] },
    { "Agent": [ "Name", "FullName", "TaxNo",
        { "TaxDepartment": ["Name", "Address"] } ] },
    { "Rows[]": [ "Qty", "Price", "Sum",
        { "Item": ["Article", "Name"] },
        { "Unit": ["Short"] } ] }
  ]
}
```

Рядок — лист (скаляр). Однопарний об'єкт — вузол (`Ref` або колекція). Корінь — `model`
endpoint-а; саме тому перевикористання бланка іншим kind-ом ловиться на збірці, а не
сюрпризом.

Різнорідність елементів масиву тут справжня — лист проти вузла, — а не цукор: різниця
несена **формою значення**, у схемі виражається через `oneOf`, опечатку не поглинає.

| Правило | Чому саме так |
|---|---|
| Кожен лист — скаляр | `"Agent"` без полів означало б «розкрий за `presentation` цілі» — і Model перестала б читатися без походу в чужу декларацію |
| `[]` на колекції обов'язковий | За інформацією це дубль (`Rows` оголошений у `details`), але без нього споживач не відрізнить колекцію від `Ref`, не відкривши metadata endpoint-а. Тому — обов'язковий і перевіряється |
| Запис повний, не дельта | Дельта понад `presentation` зробила б бланк заручником косметики: правка `presentation` у dropdown-і мовчки міняла б shape бланка. Дублювання `Name` — не ціна, а фіксація |
| `Id` не пишеться | Додається завжди. Написаний руками — теж не помилка: результат той самий |

**Колекція адресується двома іменами** — ключем `details` (усі рядки) і складеним іменем
одного kind-у (`StockRows`, [kinds.md](kinds.md)), причому обома одразу в одному бланку:
усі рядки, а нижче послуги ще раз окремо. Вибір між іменами бланк не робить.

**Масив не може висіти під `Ref`.** Глибина посилань довільна, але `[]` живе тільки на
хребті «запис → колекція → колекція». `Ref` розкривається за тотожністю, а не за
володінням — під ним не висить нічого, і оголошена там колекція мовчки втратила б рядки.

**Model — superset екранної моделі й subset поверхні.** Екран розкриває `Ref` за
`presentation` цілі (`{Id, Name}` за замовчуванням, [metadata.md](metadata.md) →
`presentation`); бланку треба глибше й ширше. Обидві — усічення одного транзитивного
замикання по `Ref`, тому перевірка одна на обидві: резолвити сегменти зліва направо по
деклараціях цілей. Глибина довільна, цикли не заважають — шлях скінченний.

## Чому Model оголошується

Model — це **запит**: те, що дістається з бази й передається рендереру. Layout —
споживач того, що прийшло. Напрямок один: спершу модель, потім бланк по ній.

**Рендерер Model не читає** — ячейка резолвиться проти того, що прийшло: проти елемента
колекції всередині діапазону, проти кореня моделі поза ним. Потрібна вона генератору
вибірки. Але місце своє виправдовує не цим: це **єдина перевірна поверхня бланка**.
Layout великий, його ніхто не читає й не резолвить; Model — двадцять рядків, які
валідатор проходить посегментно, а людина проглядає очима. Тому бланк, написаний не з
нуля — перенесений із чужої системи, відновлений із заповненого зразка, — ділиться
надвоє: існування кожного поля й вид кожного вузла ловить збірка, а неоднозначність, яку
не ловить ніхто (`Name` чи `FullName`), стоїть в одному короткому блоці замість того, щоб
бути розмазаною по двохстах ячейках.

Звідси ж надлишковість, обґрунтована в таблиці вище двічі — повний запис замість дельти й
обов'язковий `[]`: перевіряти можна тільки надлишкове, дельті нічого протиставити.

Звідси все інше. Model одна на обидва формати — ячейка Workbook, QR, елемент Page читають
ті самі шляхи, і формат layout-а нічого в ній не міняє. Питання
«хто автор Model» на формат не впливає: форма дерева однакова, хто б його не написав. І
ячейка, що читає непроголошене, малює порожньо — узгодженість тримає автор, а не
перевірка.

## Що перевіряється, а що падає в рантаймі

**Збірка:**
- корінь — рівно одна пара, і її ім'я збігається з `model` таблиці;
- кожен шлях Model резолвиться в деклараціях сегмент за сегментом, останній — скаляр;
- `[]` збігається з видом поля: `details` без `[]` — помилка, `Ref` із `[]` — помилка,
  `[]` під `Ref` — помилка;
- кожен шлях `header` резолвиться так само, тільки крізь `Ref`.

**Рантайм:** те, що читає ячейка або код бланка, з Model **не звіряється**. Промах дає
порожню ячейку або `undefined`, який тихо склеїться в рядок. Це не пропущена перевірка:
layout споживає модель, а не оголошує її.

## Що в Model НЕ пишеться

- **Фільтр рядків, сортування, агрегати по підмножині** — це запит, а не склад даних.
  Знадобиться — окремий ключ поруч; Model не псується.
- **`Ranges`** — це collection-scope ([forms.md](forms.md)) у координатах сітки: інтервал
  рядків плюс шлях до колекції. Інтервал — layout, а шлях дублює `[]` з Model і розійтися
  з ним може мовчки: діапазон над неоголошеною колекцією зникає разом із блоком. Окремого
  елемента `Document.Rows` у Model це не вимагає — він випливає з `Rows[]`.
- **`presentation` цілі** — Model перелічує поля явно і `presentation` не чіпає.

## Відкинуте

| Що | Чому |
|---|---|
| Kind `printform` | Kind дає endpoint: URL, права, пункт меню. У бланка немає нічого з цього |
| Плоский список шляхів (`"Document.Agent.FullName"`) | Model описує shape, а shape — дерево; листям воно відновлюється префіксним злиттям при кожному читанні, `Rows` не відрізняється від `Agent` без походу в декларацію, і одна модель має два написання |
| `{ model, layouts[] }` | SQL генерується на бланк — групування нічого не зливає. Union плоских Model і так тривіальний, а рівень вкладеності платять усі читачі формату. Спільна Model, якщо колись заболить, виноситься окремим файлом без зміни форми списку |
| Model як дельта понад `presentation` | Споживач не знав би, чи прийде `Name`, не резолвлячи чужий каталог; а ячейка звертається до `Agent.Name` напряму |
| Вивід Model розбором layout-а | Інвертує залежність: Model — запит до бази, layout — її споживач. До того ж layout не один (Page і Workbook), а Model для них спільна |
| Trait `Print` | Питання «чи друкує цей endpoint» уже має відповідь — склад `printForms`. Trait був би другим написанням того самого, здатним із ним розійтися |
| Заборона писати `Id` | Бланк законно друкує `Id` — QR-код, штрихкод, службова помітка. Валідатор мовчить в обох випадках |

## Нерегулярний бланк

Eject у рукописний хендлер, як і всюди: континуум матеріалізації, без лазівок у форматі.
