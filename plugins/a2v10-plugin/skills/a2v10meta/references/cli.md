# CLI `a2`

Один інструмент на всі режими. Metadata-driven — це завжди **розширення** raw, яке відрізняється одним підключеним пакетом; для CLI ціна цього — одна DLL у поставці.

## Основний принцип: CLI для LLM, не для людини

CLI в цьому проекті — інструмент для LLM. Це змінює все.

**Людський CLI** — частина діалогу з часом: людина пам'ятає попередні команди, читає кольоровий вивід, використовує tab-completion, запускає `init` щоб не писати 10 файлів з голови.

**LLM-CLI** — кожен виклик ізольований. LLM отримує тільки те, що повернула команда. Якщо не повернула — не знає. Файли LLM пише сам.

### Що з цього випливає

**Немає:**
- `init` / `new` — scaffold команди. LLM копіює `scaffold/` і пише файли напряму ([onboarding.md](onboarding.md) → Phase 2). Init додає зайвий крок: «створити шаблон → прочитати що створилося → змінити». LLM просто пише одразу правильно.
- `--help` оптимізація — LLM читає reference .md, не help.
- Інтерактивних промптів — "Are you sure? [y/N]" зависне. Ніколи, ні за яких умов.
- ANSI кольорів — шум для парсера.

**Немає й опції `--verbose`**: вона означала б, що є режим, у якому команда каже неповну правду. Повнота — не режим, а форма виводу.

**Є:**
- JSON вивід за замовчуванням (не `--json` флаг як opt-in, а завжди).
- Повний опис що змінилося, не тільки success/fail — LLM потребує знати новий стан.
- Verbose за замовчуванням — парадокс: людина хоче стислість, LLM хоче повноту.
- Ідемпотентність — безпечно запустити двічі.
- Структуровані помилки з `available` / actionable guidance.
- Ненульовий exit code при `success: false` — щоб зрив було видно й тому, хто виводу не читає.

## Один бінарник, форма `a2 <об'єкт> <дія>`

Раніше тут було описано розділення на `a2` (платформа) і `a2meta` (метадані). Воно не виправдалось.

**Чому не два бінарники.** Невідома підкоманда може повернути структуровану помилку зі списком доступних — LLM відновиться за один крок. Невідомий бінарник повертає `command not found` від шелла: без JSON, без `available`, і LLM не відрізнить «не встановлено» від «я переплутав ім'я». Гірший випадок ще тихіший: `a2 validate` і `a2meta validate` — два різні `validate`, і виклик не того просто зробить не те, мовчки й успішно. У плоскому просторі одне ім'я не може означати дві речі.

**Простір імен розділено за власником, і поділ односторонній.** `db` — префікс базового скіла; ним користуємось і ми. `meta` — наш, і назад це не працює: raw-CLI у нього не пише.

Та сама включеність (команди meta **містять** команди raw) читається саме так: не диз'юнктні простори, а вкладені, і префікс кодує, хто чий. Тому деплой метаданих — **`a2 meta deploy`**, а `a2 db …` лишається за операціями над базою, спільними для обох сторін.

## Команди

Усі команди повертають один конверт — `{success, data, error}`. У колонці «Вивід» нижче — вміст `data`.

| Команда | Що робить | Вивід |
|---|---|---|
| `a2 app config` | Конфігурація застосунку — див. нижче | `{multiTenant, metadataEnabled, hostRoot, modules[]}` |
| `a2 validate [path]` 🚧 | Перевіряє metadata.json. path = endpoint або весь проект | `{valid, errors[], resolved}` |
| `a2 effective <endpoint>` 🚧 | metadata.json з усіма застосованими умовчаннями — те, що платформа реально бачить | `{...full resolved metadata}` |
| `a2 meta deploy` | Уся послідовність деплою (див. `deploy_and_migrations.md`) | `{applied, file}` |
| `a2 meta materialize <endpoint> <action> view\|template` | Записує згенерований view або template у файл, щоб правити руками — див. нижче | `{endpoint, action, what, files[], modelJson}` |

🚧 — команди в CLI ще немає. Не викликати: відповідь буде помилкою невідомої підкоманди, а не перевіркою.

Команди `release`, `diff` і `status` з попередньої конструкції місця не мають:

- **`release`** — артефакти генеруються завжди і завжди закомічені, окремої дії «зібрати реліз» не існує;
- **`status`** («чи синхронізована БД») — це хеш, і `deploy` перевіряє його сам першим кроком;
- **`diff`** («що зайве в базі») — відповідь пише сама процедура зведення в таблицю `a2meta`, і читати її можна коли завгодно, а не лише в момент деплою.

## `a2 app config` — чи є застосунок metadata-driven

```json
{ "multiTenant": false, "metadataEnabled": true, "hostRoot": "WebApp",
  "modules": [ { "prefix": "", "root": "MainApp" }, { "prefix": "$admin", "root": null } ] }
```

**`metadataEnabled`** — єдина відповідь на питання «це metaapplication?». Ознака не файлова: команда відкриває csproj хоста й дивиться, чи є `PackageReference Include="A2v10.Metadata"`. Тобто застосунок стає metadata-driven **підключеним пакетом**, а не декларацією в репозиторії; другий кінець — `services.UseAppMetadata()` у `Startup.cs` хоста, і його прапорець не перевіряє.

`false` → у проєкті metadata-рантайму немає: писати `metadata.json` нікуди, спершу онбординг (`SKILL.md` §6).

Решта полів — `multiTenant` (режим розгортання), `hostRoot` (папка хоста), `modules` (`prefix` — літеральний токен URL разом із `$`; `root` — папка з коренем від кореня проєкту, `null` = локальної папки немає, писати нікуди).

## `a2 meta materialize` — дефолтний екран текстом

Платформа генерує екран з `metadata.json` на льоту. Команда пише те саме у файл — той самий генератор, що й у рантаймі, — щоб далі правити руками. SQL при цьому лишається на шарі метаданих: матеріалізується **екран**, не дані.

```
a2 meta materialize catalog/agent edit view
a2 meta materialize catalog/agent edit template
```

- `<endpoint>` — папка ендпоінта, два сегменти (`catalog/agent`, `$module/document/waybill`). Глибший шлях — помилка, не обрізання.
- `<action>` — `index`, `browse` або `edit`. `showtrans` і `print` не форми, вони виводяться з декларації і не матеріалізуються.
- Третій аргумент **обов'язковий** і один за виклик, бо ціна володіння різна:
  - `view` пише `<action>.view.vxaml` (сторінка) або `<action>.dialog.vxaml` (діалог). Свій view втрачає перевірку при завантаженні: `forms` у `metadata.json` резолвиться проти shape і падає на опечатці, xaml біндиться рядками — перейменоване поле мовчки рендериться порожнім.
  - `template` пише `<action>.template.ts` і `<action>.d.ts`. Свій template втрачає **правила**: required, computed, inherit, totals, стан табів скомпільовані у згенерований, і правило, дописане в `metadata.json` пізніше, до рукописної копії не доїде. Тому починати треба з матеріалізованого тексту, а не з нуля.
  - `browse template` — відмова: browse виконує template від index і його `.d.ts` імпортує `./index`. Матеріалізуйте `index template` і напишіть `"template": "index.template"` під `browse`.

**Ніколи не перезаписує.** Файл є → відмова з його іменем, і виклик пише все або нічого. Повторна матеріалізація — «видалити файл і запустити ще раз». Єдиний виняток за власником, не за прапорцем: `<action>.d.ts` — типи моделі, compile target shape, — перезаписується щоразу; його не правлять.

**`model.json` не редагується.** Це файл автора. У відповіді приходить фрагмент, який робить файл видимим для платформи, і автор зливає його сам:

```json
{
  "success": true,
  "data": {
    "endpoint": "catalog/agent",
    "action": "edit",
    "what": "view",
    "files": [ "catalog/agent/edit.dialog.vxaml" ],
    "modelJson": {
      "model": "$meta",
      "dialogs": { "edit": { "view": "edit.dialog" } }
    }
  }
}
```

`"model": "$meta"` — перемикач «дані з шару метаданих цієї папки»: четверте значення ключа `model` поряд з `""` (екран без моделі), іменем (процедури) і `$sql:key` (текст). Наслідується від кореня до дії, як `model` завжди: `$meta` у корені і `"view"` на одній дії — та дія з власним екраном, решта згенеровані. `view` і `template` беруться незалежно: що написано — з файлу, чого нема — генерується. Папка без `model.json` — усе згенероване, як і було.

Матеріалізований `.vxaml` перевіряється звичайним `a2 view validate catalog/agent/edit.dialog`.

## Формат виводу `effective` 🚧

Повертає metadata після `applyDefaults()` — той самий об'єкт, який платформа використовує внутрішньо, до виконання запиту. Корисно для LLM перед записом `post.document`/`post.row` або `ui.layout`: бачить усі поля (включно з baseline) без ручного обчислення конвенцій. (`applyDefaults()` — назва платформної функції, з блоком `post` не пов'язана.)

```json
{
  "kind": "catalog",
  "schema": "cat",
  "table": "Agents",
  "model": "Agent",
  "presentation": "Name",
  "fields": {
    "Id":   { "type": "id" },
    "Name": { "type": "name" },
    "Memo": { "type": "memo" },
    "Void": { "type": "bit" },
    "Code": { "type": "string", "length": 16 },
    "..."
  },
  "ui": { "..." }
}
```

**Це read-only view.** Показує що платформа бачить, не що треба писати у файл. У файл пишуться тільки відхилення від умовчань.

## Формат виводу `db deploy`

Принцип: повертати тільки те, на що LLM реагує.

**Норма:**
```json
{
  "success": true,
  "data": {
    "applied": true,
    "file": "MainApp/_sqlscripts/deploydatabase.sql"
  }
}
```

`applied: false` означає «хеш збігся, до БД не ходили» — і це єдине поле, на яке модель реагує без помилки. Правки, що в SQL не проєктуються (`description`, `synonyms`, `triggers`), дають `false` законно. Правка поля — не дає, і `false` після неї означає, що вона пішла не в той файл.

`file` — головний модуль застосунку плюс `_sqlscripts/deploydatabase.sql`, відносно поточного каталогу; конкретна назва модуля береться з конфігурації, тому в різних застосунках вона різна. Вказує на актуальний файл в обох випадках. При `applied: false` він не перезаписується, і це не оптимізація: збіг хеша **означає**, що цей самий стан метаданих уже деплоївся повністю — і тим самим генератором теж, бо його версія лежить у сиді й у хеші. Тобто файл отримав ці самі байти тоді ж і лежить закоміченим. Відсутній файл — зламане робоче дерево, а не стан деплою; лікується git'ом, не генератором.

**Помилка:**
```json
{
  "success": false,
  "error": {
    "message": "The object 'UNQ_Agents_Code' is dependent on column 'Code'.",
    "file": "MainApp/_sqlscripts/deploydatabase.sql",
    "lineFrom": 214,
    "lineTo": 217
  }
}
```

Помилки приходять від SQL Server як є. Не треба перекладати їх у власну таксономію: текст `The object '...' is dependent on column '...'` називає винуватця точніше за будь-який `kind`.

`lineFrom`/`lineTo` — межі батча, на якому впало. Скрипт виконується батчами по `go`, тому впав рівно один, і оскільки виконується **той самий текст, що записаний у файл**, межі батча є координатами у `deploydatabase.sql`. Модель дочитує фрагмент сама.

Тексту батча у відповіді немає навмисно. Він уже лежить на диску — класти його ще й у відповідь означає копіювати артефакт у повідомлення замість того, щоб указати в нього. І тільки координата має однорідну форму: батч на два рядки і сид на чотириста описуються нею однаково, тоді як текстом довелося б розводити випадки — сидовий MERGE це десятки кілобайт, у яких помилка все одно називає значення, а не місце. Зникнення цього окремого випадку і є ознака, що розріз правильний.

Обрізати текст замість цього не можна: обрізаний SQL гірший за відсутній — модель полагодить те, що бачить, а не те, що впало.

`file` дублюється в `error` не для симетрії: при провалі `data` порожня, а без імені файлу дві цифри не значать нічого.

Діапазон на рядок ширший з кожного краю — захоплює рядок з `go`. Це наслідок того, що розділювач забирає перевід рядка з собою, і виправляти його не треба: вміст батча він покриває завжди.

Курованого словника warning'ів немає, і це не спрощення виводу, а наслідок конструкції: **уся політика «що робити, коли не збіглося» живе в `a2meta.SyncSchema`**, всередині БД. CLI не приймає рішень, тому й доповідати про прийняті йому нічого. Те, що процедура вирішила лишити без змін, вона сама записує у свою таблицю зайвого — див. `deploy_and_migrations.md`.

Оскільки хеш пишеться останнім, повторний запуск після помилки безпечний і продовжить з того ж місця. Реагувати треба правкою `metadata.json`: `deploydatabase.sql` — згенерований артефакт, будь-яка правка в ньому зникне на наступному прогоні.

## Чому не MCP

MCP виправданий коли:
- Потрібна persistent session (дорогий старт — тисячі файлів, connection pool).
- Немає shell (web-Claude, корпоративний чат-бот).
- Інструмент shared між багатьма LLM-клієнтами одночасно.

В цьому проекті:
- 100 metadata.json × 1KB = 50ms cold start. Не відчутно.
- Claude Code має shell. Bash tool покриває все.
- MCP = та сама C# бібліотека + протокол зверху = складність без користі.

**Висновок:** CLI через Bash tool і пряма робота з файлами через Read/Write покривають усі потреби LLM без додаткового шару.
