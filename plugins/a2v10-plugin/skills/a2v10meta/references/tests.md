# Тести — сценарії

`a2 meta validate` каже, що endpoint зібрався; `a2 meta deploy` — що схема лягла в базу. Що застосунок робить те, що просили, не каже жодна з них: проведення з переплутаним `dir` збирається, деплоїться й рендериться. Це каже **сценарій** — файл, який проходить крізь застосунок тими самими дверима, що й браузер, і звіряє результат із вимогою.

## Правило

**Сценарій формулює факт із вимог словами користувача — і ніколи не переказує ключ `metadata.json`.**

Перевірка: якщо очікуване значення можна вивести, прочитавши лише `metadata.json`, — це копія декларації. Вона проходить завжди й не ловить нічого. Видали її.

- копія: «після `post` у `journal/stock` є рядок з `InOut = 1`» — це блок `post`, записаний удруге;
- тест: «прихід 10 на склад А, переміщення 3 у Б → залишки А = 7, Б = 3» — ці числа беруться лише з вимоги, і переплутаний `dir` їх зламає.

Для довідника вимога зазвичай — «зберіг → відкрилось те саме». Такий сценарій законний: очікуване береться з вимоги, не з декларації.

## Де лежить і чим запускається

```
<застосунок>/
  MainApp/
  WebApp/
  Tests/
    scenarios/        ← твоє: один файл — один сценарій
    Tests.csproj, *.cs ← не твоє
```

- Пишеш тільки `Tests/scenarios/*.json`. Решта `Tests/` — оболонка зі `scaffold/`, як `WebApp`; раннер — у пакеті платформи. Без сценаріїв прогін зелений: рядок сценаріїв пропущено, не впав.
- **Один файл — один сценарій — один рядок у списку тестів.** Ім'я рядка — шлях файла в `scenarios/` без розширення (`stock-move`, `stock/move`). Кроки тестами не є: кожен спирається на попередній, перший невдалий названо в повідомленні.
- Усі сценарії: `dotnet test Tests`. Один: `dotnet test Tests --filter "DisplayName~stock-move"`.
- Запускати **після** `a2 meta deploy`, на кожну вимогу — свій сценарій.

**База.** Прогін працює в окремій базі `<база з ConnectionStrings.Default>_Test` на тому ж сервері. Раннер створює її сам на початку прогону (`full.sql` зі збірки хоста, потім деплой метаданих) і лишає після: на ній можна відкрити застосунок і подивитись стан. Базу автора прогін не читає й не пише. Ім'я виводиться, не оголошується — налаштовувати нічого.

Користувач усіх кроків — `99`, єдиний, якого `full.sql` створює в порожній базі.

## Формат

```json
{
  "requirement": "Переміщення між складами проводиться, і документ це показує.",
  "records": {
    "apple": { "at": "/catalog/item",  "data": { "Name": "Яблука" } },
    "main":  { "at": "/catalog/store", "data": { "Name": "Головний склад" } },
    "shop":  { "at": "/catalog/store", "data": { "Name": "Магазин" } }
  },
  "steps": [
    { "do": "save", "name": "mv1", "at": "/document/waybillmove", "data": {
        "Date": "2026-09-02", "StoreFrom": { "ref": "main" }, "StoreTo": { "ref": "shop" },
        "StockRows": [ { "Item": { "ref": "apple" }, "Qty": 3, "Price": 5, "Sum": 15 } ] } },
    { "do": "post", "name": "mv1" },
    { "do": "expect", "record": "mv1", "data": { "Done": true } }
  ]
}
```

Цілком, на застосунку — `examples/warehouse/Tests/scenarios`: `item-card` — довідник, правка за тим самим ім'ям і обидві форми `expect`; `stock-move` — таблиця без видів, тому колекція там `Rows`, а не `StockRows`, як вище; `stock-balance` — залишки звітом.

| Ключ | Що це |
|---|---|
| `requirement` | обов'язковий. Факт, який сценарій перевіряє, — він же перший рядок повідомлення про падіння. Пиши лише те, що кроки справді перевіряють |
| `records` | записи, на яких стоїть сценарій: ім'я → `{ at, data }`. Створюються по черзі, раніше названі доступні через `ref` |
| `steps` | кроки, по черзі |

| Крок | Ключі | Що робить |
|---|---|---|
| `save` | `name`, `at`, `data` | нове ім'я — новий запис; відоме ім'я — правка того самого запису (`at` мусить збігатись) |
| `post` / `unpost` | `name` | проводить / розпроводить документ. Адреса береться із запису |
| `expect` | `record`, `data` | відкриває запис і звіряє названі поля |
| `expect` | `at`, `list` | відкриває список і звіряє рядки |
| `expect` | `report`, `rows`, `filter`, `groupBy` | будує звіт і звіряє рядки (version >= 8674) — «Звіт» нижче |

**`at`** — адреса endpoint-а, як у меню: `/catalog/agent`, `/document/waybillmove`. Раннер відкриває лише `catalog` і `document`; звіт — лише крок `expect report`.

**`data` — модель, яку отримує екран, а не таблиця:**
- поля запису — на верхньому рівні `data`, без обгортки моделі;
- колекція з видами приходить окремою колекцією на вид: `<Вид><Ключ колекції>` — `StockRows` для виду `Stock` у `Rows`. У `metadata.json` це ім'я не пишеться ніколи, у сценарії — тільки так;
- посилання — об'єкт. На запис сценарію — `{ "ref": "<ім'я>" }`. На запис, якого сценарій не створює (рахунок з `seed.json`), — його ключ: `{ "Id": "361" }`;
- `Id` записів сценарію не пишеться ніде: їх генерує база;
- дата — `"yyyy-MM-dd"`.

**`save`** нового запису стартує з того, з чого стартує екран, — з `initialValues`. Колекцію в `data` замінено цілком: рядки, яких немає в `data`, видаляються.

**`expect record`** звіряє тільки названі поля: чого сценарій не назвав, того він не стверджує. Колекція звіряється цілком — кількість рядків і порядок, у рядку — названі поля. Ім'я поля, якого в моделі немає, — падіння, не мовчання.

**`expect list`** звіряє **повний набір** записів цього сценарію за адресою `at` — не «містить»: зайвий рядок теж падіння. Порядок не важить. Записи інших сценаріїв не враховуються — база в прогоні спільна.

## Звіт (version >= 8674)

Залишки, обороти, сальдо, кореспонденції перевіряються звітом — тим самим, що бачить користувач.

```json
{ "do": "expect", "report": "/report/stockturnover", "groupBy": [ "Store", "Item" ],
  "rows": [
    { "Store": { "ref": "main" }, "Item": { "ref": "apple" }, "EndQty": 7, "EndSum": 35 },
    { "Store": { "ref": "shop" }, "Item": { "ref": "apple" }, "EndQty": 3, "EndSum": 15 } ] },
{ "do": "expect", "report": "/report/trialbalance", "filter": { "Company": { "ref": "firm" } },
  "rows": [
    { "Acc": { "Id": "281" }, "DtSum": 50, "DtEnd": 50 },
    { "Acc": { "Id": "631" }, "CtSum": 50, "CtEnd": 50 } ] }
```

- **`groupBy`** — з `groups` звіту, по порядку; у звіту з `groups` — обов'язковий. `trialBalance` і `chessboard` мають рядки за рахунком, `groupBy` не пишеться.
- **`filter`** — `Period` як `{ "From": "yyyy-MM-dd", "To": "yyyy-MM-dd" }` (немає — усі дати); вимір з `filters` звіту — посиланням. Ім'я, якого звіт не знає, — падіння.
- **Імена чисел у рядку** дає тип звіту:

  | Тип | Рядок |
  |---|---|
  | `turnover` | групи з `groupBy`; на кожне `data`: `Start<Д>`, `In<Д>`, `Out<Д>`, `End<Д>` — `EndQty`, `InSum` |
  | `trialBalance` | `Acc`; `DtStart`, `CtStart`, `DtSum`, `CtSum`, `DtEnd`, `CtEnd`; `OffBalance` |
  | `chessboard` | `Acc` — рахунок дебету; `Sum`; `Cross` — `[ { "Key": "<рахунок кредиту>", "Sum": … } ]` за зростанням коду: колекція звіряється з порядком |

  Рахунок — `{ "Id": "<код>" }`.
- **`rows` — повний набір рядків сценарію**, як в `expect list`: зайвий рядок — падіння, порядок не важить, у рядку — лише названі числа.
- **Звіт складає всю базу прогону**, а вона спільна. Тому числа — цього сценарію, лише коли їх обмежує його запис:
  - `filter` за записом сценарію (своя компанія, свій склад) — звіряються всі рядки;
  - інакше — лише рядки, в яких група — запис сценарію;
  - ні того, ні іншого — падіння: такі числа залежать від того, що прогнали раніше.

  Тому в кожному сценарії свої записи вимірів. `trialBalance` і `chessboard` групують лише за рахунком — їх обмежує тільки `filter` за записом сценарію (своя компанія). У звіту без такого виміру в `filters` сальдо й кореспонденції сценарій не перевірить: скажи автору.

## Чого сценарій не бачить

- **Правила, які живуть лише на клієнті** — `properties`, `required`, `inherit` виконує `template.ts`, двері їх не запускають. Тому `Sum` рядка сценарій пише сам, і очікування на обчислене значення не пишеться: воно перевіряло б власну арифметику сценарію.
- **Журнал, ledger, план рахунків** напряму не відкриваються: рядок проводки — це блок `post`, записаний удруге; числа з них дає звіт.
- **Відмову.** Кроку «тут має бути відмова» немає: сценарій перевіряє лише те, що проходить.

## Тест упав

- **Правиш декларацію, не очікування.** Змінити очікування — значить змінити вимогу, а це рішення автора.
- Повідомлення: перший рядок — `requirement`, далі крок (`steps[3] (expect)`), шлях у моделі (`Document.StockRows[0].Qty`) і пара «очікувалось / отримано». Відмова платформи на кроці приходить її власним текстом.
- **Вимога, яку норма не покриває** (наприклад, «не продати більше, ніж є на складі» — `journal.md` декларативну перевірку залишку відкидає): тест упаде, і це правильний результат. Скажи автору, яка вимога не покрита, і не вигадуй поверхню, щоб він пройшов.
