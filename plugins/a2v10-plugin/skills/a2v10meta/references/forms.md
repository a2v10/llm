# forms — модель форм

Форми metaendpoint описуються декларативно, XAML будується з опису. Блок `forms` у `metadata.json`, поруч із `fields` / `initialValues`.

**Замінив блок `ui`**, якого більше немає в [metadata.md](metadata.md). Разом з ним пішли: layout рядами (`ui.edit.layout`), per-field overrides на елементі (`required` / `readonly` / `label`) і `multilineHeight` — причини нижче, у «Чого в мові немає».

## Навіщо взагалі проміжний рівень

Описувати форми — **не задача**; XAML це робить краще. Шар виправданий рівно трьома речами, і всі три — властивості **малості**:

1. **Регенерованість** — додав поле в metadata → форма перебудувалась. Торкнув XAML руками → регенерація мертва.
2. **Мержибельність** — кастомізація як патч над структурою, а не над текстом.
3. **Пише модель** — п'ять типів вузлів написати без помилок легко, XAML — ні.

**Цінність IR — у тому, чого він НЕ може виразити.** Мова, ізоморфна XAML, — це XAML у фігурних дужках. Критерій: якщо з опису не викидається 80% — це не IR.

**Між «згенеровано» і «XAML» третього стану немає.** Це continuum матеріалізації, а не рівень абстракції. Нерегулярна форма **не описується** мовою: fail-loud → eject у XAML. Жодних `template` / `custom` / `xaml-fragment` усередині JSON: перша ж лазівка запускає сходження до XAML, бо будь-яка мова, що мусить покрити важкий випадок, доростає до цільової.

## Дві ортогональні осі: ROLE (`is`) ⟂ SCOPE

| Вісь | Ключ | Словник |
|---|---|---|
| РОЛЬ — чим вузол є | `is` | **замкнутий**: `Page` / `Dialog` / `Tabs` / `Tab` / `Group` / `TreeGrid` / `Toolbar` / `Taskpad` |
| ЯКІР ДАНИХ — до чого прив'язаний | `scope` (+ `kind`) | **відкритий**: імена з metadata |

Кожне `is` — власний тип, диспетч по таблиці `tag → Type`, без `when`. `scope` — **атрибут, а не тип**: інакше комбінаторний вибух ролей × якорів.

**Шлях у `is` — помилка.** `{ "is": "Rows" }` таблиця тегів не знайде, і конвертер змушений робити «невідомий тег → значить scope», тобто гілку в диспетчі. Правильно: `{ "is": "tab", "scope": "Rows" }`.

### `kind` — друга частина якоря

Колекція, що оголосила `kinds`, приїжджає N окремими колекціями ([metadata.md](metadata.md) → «`kinds` — види рядків»). Табличну частину одного виду адресують **двома ключами**:

```jsonc
{ "is": "tab", "scope": "Rows", "kind": "Stock" }
```

`kind` обов'язковий тоді і тільки тоді, коли колекція оголосила види: без нього вузол вказував би на всю колекцію, якої в моделі немає.

**Складене ім'я (`scope: "StockRows"`) не приймається.** Воно згенероване — так набір зветься у моделі, у параметрі збереження, у шляху валідатора, — і написане в metadata означало б, що правило композиції має дві реалізації, генератор і автора, без способу їх звірити. Це той самий принцип, за яким у metadata немає імен `properties` / `validators` ([rules.md](rules.md)): автор пише факт, ім'я обирає генератор.

## Scope — завжди відносний

- База форми = **конверт результату endpoint'а**, не колекція записів. Корінь форми робить перший re-root: `"scope": "Document"`.
- Підйом: `Root` (абсолютний якір) або `$parent`. Отже `Filter` і `Documents` — **сусіди в конверті**; до `Filter` не «переходять із колекції», до нього піднімаються через `Root.Filter`.
- Переходів рівно два: **спуск по властивості** та **ітерація**. Решта — підйом.
- `scope` успадковується вниз (як DataContext); лист `scope` не несе — лише відносний шлях.
- `Root` стійкий до переносу всередині конверта і ламається при переносі в інший; `$parent` — навпаки. **Фрагменти для повторного використання пишуться на `$parent`, ніколи на `Root`.**
- **`$parent` = найближчий об'ємний RECORD**, не «один scope вгору»: `Rows` + `[i]` — два кроки, поп-один дає колекцію (нікому не потрібна), поп-два дає запис (завжди те). Так `$parent` ще й kind-типізований: завжди `record`.

## Запис і колекція — два вузли

**`Group` — редактори запису, `Tab` — рядки колекції.** Не один вузол із виведеною кардинальністю: `axis` і `labelAt` групи описують розкладку редакторів і над рядками нічого не значать, а `kind` табу нічого не значить над записом. Ключ, чий сенс залежить від того, у що резолвився `scope`, — той самий дефект, що й іменовані регіони нижче.

Тому **`scope` пишеться лише на `tab`, а `tab` — лише всередині `tabs`**; інше — помилка збірки. Колекція без видів — смуга з одним табом. Слів `table` / `grid` / `checkbox` у мові немає. Column ≡ edit-control (обидва — лист на record-scope).

**Kind-чек fail-loud:** презентер вимагає свій kind, невідповідність = помилка збірки. Kind-чек ще й підказує, куди класти вузол (див. «Розв'язані кейси»).

Контрол виводиться з **домену поля**, не з форми: `Bool` → чекбокс, `Ref` → лукап, `Memo` → textarea, `Date` → пікер. Захотілось написати контрол у формі — домен описано невірно, чинити `fields`.

## Корінь і `body`

```jsonc
"forms": {
  "edit": {
    "is": "page", "scope": "Document",
    "taskpad": { "is": "taskpad", "fields": ["Company", "Project"] },
    "body": [
      { "is": "group", "fields": ["Number", "Date"] },
      { "is": "group", "axis": "rows", "fields": ["Agent", "StoreFrom", "StoreTo"] },
      { "is": "tabs", "fields": ["IsVat", "VatIncluded"],
        "elements": [
          { "is": "tab", "scope": "Rows", "kind": "Stock" },
          { "is": "tab", "scope": "Rows", "kind": "Service", "fields": ["Item", "Sum"] }
        ] },
      { "is": "group", "fields": ["Memo"] }
    ]
  }
}
```

**`body` — колекція вузлів.** Вкладеність механічно можлива й нічого не потребує: ключ `elements` уже носять `Tabs` і `Taskpad`. Плоским є **лист**: `Group` тримає лише імена полів (`fields: string[]` фізично не вкладається — depth тримає схема, не валідатор).

**Розкрій корінь не оголошує.** У `body` він фіксований — вертикальний стек із виведеною розтяжкою (нижче), тому `axis` на корені немає й бути не повинно: другий спосіб розкласти `body` конкурував би з правилом слека.

**Іменованих регіонів (`header` / `footer` / `above` / `below`) немає.** Вони мертві: сенс залежить від наявності `tabs` — немає табів, і «над/під» вказують у порожнечу. **Ключ, чий сенс залежить від наявності іншого ключа, не може бути правильним ні за якого написання.**

**Розтяжку ніхто не оголошує** — `Auto` / `*` / `Auto` виводиться: блок `tabs` забирає слек. Таких блоків нуль (нічого не тягнеться) або один; два = помилка збірки. «Memo притиснутий до низу» — наслідок того, що він **після** розтяжки, а не декларація.

**`Tabs` пишеться явно** — і без нього колекцію не показати: інших носіїв рядків у `body` немає.

## Три види дітей — жоден тип не обирає між ключами

Скільки ключів дітей і які — визначає тип. Течею було б одне `is` із двома можливими формами (гілка в диспетчі); лікується типізацією, не злиттям ключів.

| `is` | ключі дітей | тип елемента |
|---|---|---|
| `Page` / `Dialog` | `toolbar` + `taskpad` + `body` | node |
| `Tabs` | `fields` (scope хазяїна) + `elements` | ім'я поля / node |
| `Tab` / `Group` | `fields` (у `Tab` **опційний**: відсутній = весь row shape у порядку metadata) | ім'я поля |
| `Toolbar` | `commands` | ім'я команди |

```
fields:   string[]   ← листя. Масив рядків фізично не вкладається → depth=1 тримає СХЕМА, не валідатор
commands: string[]   ← імена дій, інший namespace (реєстр команд).
                       `$sep` (роздільник) — розмітка смуги, не команда.
                       Регістр значущий: цей словник єдиний, що читається
                       без ignoreCase
elements: node[]     ← піддерева
```

**Не схлопувати `fields` у `elements`**: злиття знімає стелю глибини. Три namespace'и: поля metadata / реєстр команд / вузли.

## Toolbar

**Стандартний набір команд не пишеться** — виводиться з ролі форми, kind і metadata: `Post` / `UnPost` / `ShowTrans` — з непорожнього `post`, `Print` — з `printForms` ([print.md](print.md)). Вимкнути стандартну команду не можна; не потрібна → eject.

Слот `toolbar` тримає лише **додані** команди. У стандартному наборі для них одне місце — між командами сутності і хвостом (`Reload`, `Search`); позицію обирає шаблон, не автор, тому з розмітки смуги лишився тільки `$sep`. Від стандартних додані відділяє роздільник шаблону — першим `$sep` не пишеться.

Стандартне ім'я в слоті не помилка: дає другу кнопку, і це видно одразу.

**`Toolbar` у `body` — друга смуга**, лише власні команди. `toolbar` у формі `edit` з `is: "dialog"` — помилка збірки: смуги в діалозі немає, його команди — кнопки внизу.

🟡 Власні команди не описані: ім'я в слоті поки ні на що не посилається. Кандидат — словник `commands` у самому endpoint'і, форма посилається на ім'я.

## Розкрій — `axis`

Група — потокова смуга (рендериться `FlowPanel`, тобто flex). Єдиний ключ розкрою — напрямок:

```jsonc
{ "is": "group", "fields": [...] }                  // умовчання `columns` — стовпчик
{ "is": "group", "axis": "rows", "fields": [...] }  // смуга: поля йдуть вправо
```

| Ключ | Тип | Умовчання |
|---|---|---|
| `axis` | `"columns"` \| `"rows"` | `"columns"` |

**Числа немає, і воно не потрібне.** Ширину кожного поля дає його домен, перенос робить сам потік: не влізло — поїхало на наступний рядок. Тому «три колонки» не оголошується — три колонки **виходять**, коли в смузі три поля по 22rem, а вікно ширше; на вузькому екрані те саме оголошення чесно деградує в два ряди. Розглядались і відкинуті два ключі: `count` (фіксоване число треків) і `childWidth` (спільна ширина дітей) — обидва задають те, що вже сказав домен, і обидва не переживають вузький екран.

**Умовчання — стовпчик**, бо умовчання не можна прочитати, лише вивчити: єдине безпечне те, що збігається з очікуванням (поля форми стікаються вертикально).

**Ширин, спанів, порядку обходу і точок переносу в мові немає.** Нерівний рядок = **окрема група**; голий масив ≡ група, тож зайва група коштує один рядок.

**Вирівнювання між рядами потік не дає.** У однорідній смузі краї збігаються самі (три `Ref` підряд — усі однієї доменної ширини), у різнорідній будуть рваними, і поправити це в мові нічим. Це прийнята ціна: вирівнювання вимагало б треків, треки — числа, а число повторювало б те, що вже сказав домен.

## Ширина і розтяжність — властивість домену

У формі не оголошуються **взагалі**. Генератор ставить на контрол клас домену, значення живуть у стилях платформи:

```less
.flow-panel {
  .dom-memo { flex: 1 1 auto; }                  // тягнеться, забирає решту смуги
  .dom-date { width: 14rem; max-width: 14rem; }  // не росте, може стиснутись
  .dom-ref  { width: 22rem; min-width: 22rem; }  // не стискається
}
```

Тут самі собою виражені всі чотири величини розмірної моделі (`basis` / `min` / `max` / `grow`) — але **по одному разу на домен**, а не на кожному елементі. 1С тримає їх на елементі саме тому, що доменів у неї немає; у нас є, тому в metadata не пишеться нічого.

Три умови, щоб це не поїхало:

1. **Носій один.** Якщо ширина живе в CSS, білдер не має емітити `Width` у XAML — інакше два джерела одного факта, і при розбіжності виграє випадковий.
2. **Ширина залежить від контексту, не лише від домену.** `Ref` у смузі — одна ширина, `Ref` у колонці таблиці — інша. Це селектор-предок (`.flow-panel .dom-ref` проти `.data-grid .dom-ref`), а не другий клас.
3. **Фолбек для незнайомого домену** — базове правило без модифікатора має давати притомний результат само собою.

## `labelAt`

Де стоїть підпис відносно контрола. Ортогональне до розкрою.

```jsonc
{ "is": "group", "axis": "rows", "labelAt": "left", "fields": ["Number", "Date", "ExtNumber"] }
{ "is": "group", "axis": "rows", "fields": ["Agent", "Contract", "Role"] }  // підписи зверху
```

| Ключ | Тип | Умовчання |
|---|---|---|
| `labelAt` | `"top"` \| `"left"` | `"top"` |

**Властивість смуги, не поля.** Усередині однієї смуги підписи стоять однаково; per-field розміщення одразу вимагало б правила злиття. **Словник закритий** (`Top` / `Left`), невідоме значення падає. `Right`/`Bottom` — за реальним випадком; чекбокс ним не буде: розміщення його підпису диктує домен контрола, а не смуга.

Чому саме це ім'я: не `label` — слово вже означає ключ локалізації підпису; не `orientation` — на цьому ж вузлі живе `axis`, і «орієнтація групи» проти «орієнтації підпису» плутається гарантовано; не `labelPosition`/`labelPlacement` — це імена з UI-бібліотек, і разом з іменем приїжджає їхній словник значень (`start`/`end`/`bottom`), якого тут немає.

**Не успадковується.** І це загальне правило форми, а не властивість цього ключа:

> Успадковується тільки `scope` — бо він про **дані**: шлях відносний, дитина фізично не може знати абсолютний якір. Усе, що про **вигляд**, вузол оголошує сам.

Три причини: вигляд вузла має читатися по самому вузлу, без підйому по дереву; вкладають саме тоді, коли всередині треба **інакше**, тож каскад вірний якраз там, де вкладеності немає; і успадковане робить фрагмент непереносимим — перенесений в інший контейнер він міняє вигляд, хоча в ньому нічого не міняли (той самий довід, що «фрагменти пишуться на `$parent`, ніколи на `Root`»).

**Ширини підпису немає.** При `labelAt: "left"` підпис займає своє, ввід забирає решту смуги. Клас висить на **панелі**, а не на кожному контролі: `labelAt` — властивість смуги, тож і носій має бути один на смугу, а не продубльований по дітях.

```less
.flow-panel {
  &.label-at-left {
    .control-group {
      display: flex;
      flex-direction: row;
      white-space: nowrap;
      gap: 1rem;
      align-items: baseline;

      .input-group { flex: 1 1 auto; }
    }
  }
}
```

`align-items: baseline` (а не `center`) — щоб підпис сідав на базову лінію тексту вводу й не з'їжджав у середину, коли поруч багаторядковий `Memo`. `white-space: nowrap` — щоб підпис не ламався; ціна в тому, що довгий підпис витискає ввід замість переносу.

Підписи сусідніх рядків при цьому **не вирівнюються**: у потоці немає треків, вздовж яких їх можна було б вирівняти. Той самий прийнятий обмін, що й у розкрої; лікується вибором `"top"`.

🟡 **subgrid — знято.** Вирівнювання підписів через подвоєння трек-листа і `subgrid` на обгортці має сенс лише в гридовій гілці, а гридової гілки в мові немає. Якщо колись повернеться число треків — повертати разом із ним.

## `title`

`title` на групі → `Header` того самого `FlowPanel`; окремої обгортки `Panel` не потрібно — носій заголовка один і той самий, що носій розкрою. Значення — ключ локалізації, не текст.

🟡 Поведінка (статична / згортна / спливна) і початковий стан: контрол це вміє (`FlowBehavior`, `Collapsed`), ключів у мові поки немає. На корпусі 1С, яким перевіряли, заголовків і згортання **не виявилось узагалі** — усі 17 груп із `ShowTitle=false`, `Representation=None`. Тож додавати за реальним випадком, а не наперед.

## Ім'я слота = властивість хазяїна

`Page.Taskpad` тримає `taskpad` без абсурду з тієї ж причини, що `Grid.Row` тримає будь-що: **ім'я слота належить хазяїну, `is` — дитині.** Тому `is: "taskpad"` усередині слота `taskpad` не надлишковий: завтра там буде `drawer`.

| Слот названо | Доля |
|---|---|
| за відношенням до сусіда (`above` / `below`) | повисає, коли сусіда нема → мертвий |
| за вмістом (`memo`, `totals`, `attachments`) | звалище, slot creep, росте перерахуванням → мертвий |
| **як властивість хазяїна** (`toolbar`, `taskpad`, `body`) | визначений завжди, тримає будь-яку роль → живий |

## Поверхня vs AST

> **Поверхня може мати кілька написань. AST — рівно одне.**
> Написання допустиме, якщо (а) не здатне поглинути помилку і (б) конфлікт написань падає гучно.

- **Голий масив ≡ `{ "is": "group", "fields": [...] }`** — живе: інша форма, помилка в неї не провалюється, економить рядки на кожній групі.
- **Розщеплення по комі** (`"fields": "A, B"` або `["A, B"]`) — **мертве**: пропускає одруківку наскрізь. `["Company, Project"]` = поле з комою в імені = помилка збірки.
- Поверхневий цукор помирає в конвертері, до AST не доїжджає.

## `readonly` — не в моделі взагалі

Їде в payload системною колонкою запиту (`[!!ReadOnly] = 1`). Ні форма, ні metadata про нього не знають — і не «за kind»: прапор приходить із **кожною** відповіддю, тому один документ буває редагований чи ні за правами або станом; статичним він бути не міг.

- `ReadOnly = 1` → контрол не рендериться зовсім, на клієнт іде `<span>`. Це не стан контрола, а **інший презентер**. Наслідок: **окремої view-форми не існує** — одна форма, два рендери.
- **Генераторів два:** *збірковий* (metadata → XAML, знає домен, обирає сімейство контрола) і *запитний* (XAML + payload → HTML, знає прапор, обирає редагованість). AST прапора не бачить.
- Тому `{ "field": "Sum", "readonly": true }` у формі — build-time факт проти runtime факту, знадобилося б правило злиття, тобто `when`.
- Не плутати два `readonly`: **об'єктний** (системний прапор, runtime, весь результат) і **польовий** (`Sum` обчислюваний — властивість домену, build-time).

## Чого в мові немає і не буде

- **Об'єкти на полі** (`{ "field": "Sum", "readonly": true }`) — це домени. Захотілось написати → домен описано невірно, чинити `fields`.
- **`required` на полі форми** — модельний факт, не оформлення: блок `rules` у metadata ([rules.md](rules.md)). Форма лише показує позначку й вішає `ValidRequired` на команду свого шару.
- **Контроли** (`checkbox`, `table`, `controls`) — виводяться з домену.
- **Caption панелей як вільний текст** — локалізація.
- **`grid.row`, ширини, спани, розкладка окремого поля.**
- **Окрема «форма перегляду»** — див. `readonly`.

## Розв'язані кейси

**Чекбокси на смузі табів** — без eject і без розширення мови:

```jsonc
{ "is": "tabs", "fields": ["IsVat", "VatIncluded"], "elements": [ /* tab, tab */ ] }
```

Не `commands` (це стан, а не дія — інший namespace) і не `controls` (чекбокс — бо домен `Bool`). **Вузол вибирає не око, а kind-чек:** у `Tab` є `scope: "Rows"` → рядок → `IsVat` не резолвиться; у `Tabs` scope немає → успадковує `Document` → резолвиться. Позицію (смуга) диктує хазяїн.

**Одна смуга — одна колекція.** Стан смуги (який таб відкрито) живе властивістю на коллекцію, тож табам двох різних колекцій нема на чому ділити один перемикач. Дві табличні частини — дві смуги; збірка форми, де в одному `Tabs` зійшлися різні `scope`, падає.

**Журнал / index — не `Group`.** Список генератор будує роллю таблиці з пейджером і фільтрами, а цих ролей у словнику `is` ще немає — див. «Відкрите» 1. Доки їх немає, `forms.index` написати нічим: без нього список будується за замовчуванням.

**Дерево — `treeGrid`.** Index плану рахунків за замовчуванням — один вузол `treeGrid` із `fields`; перша колонка несе кнопку розгортання. Дерево прив'язане до колекції напряму: пейджера, фільтрів і пошуку в нього немає, модель приходить цілком ([accplan.md](accplan.md) → «Екрани»). SQL дерева сьогодні будується лише для `accplan`: `treeGrid` у формі іншого kind-а даних не отримає.

## Eject

**Частка eject — 5–10% форм** (оцінка автора, 2026-07-08). Решта лягає в мову; шар окупається.

Після eject файл належить розробнику, і робити з цим більше нічого не треба: ні signal-of-staleness, ні версій metadata, ні метрик churn — це специфічний випадок під повним контролем, а не проблема, що потребує інфраструктури.

## Стан реалізації

Факти з генератора (`A2v10.Metadata/Meta/FormMetadata.cs`, `Form/*.cs`) на 2026-07-28 — не частина специфікації, а те, що вже є:

- Корінь: `Page` / `Dialog`; слоти `Body`, `Toolbar`, `TaskPad`.
- Вузли: `Group`, `Tabs`, `Tab`, `DataGrid`, `TreeGrid`, `Taskpad`, `Toolbar`, `Pager`, `Filters`.
- Вузол: `Is`, `Scope`, `Elements`, `Fields`, `Commands`, `Axis` (умовчання `Columns`). `Count` був заведений і **прибраний** разом із гридовою гілкою.
- Команди toolbar (замкнутий словник): `Create`, `Edit`, `Delete`, `Save`, `SaveAndClose`, `Print`, `Copy`, `Show`, `ShowTrans`, `Search`, `Reload`, `Post`, `UnPost`, `Attachments` + `$sep`. Стандартний набір будує шаблон (`XamlBuilder.StandardToolbar`), `DefaultFormBuilder` смуг не створює.
- `ShowTrans` — діалог рухів документа: що саме він проводить, у які журнали й на які суми. Набір журналів береться з `post` — при зіставленні з `journal` кожного запису, при проводці процедурою з її `journals` ([metadata.md](metadata.md) → `post`).
- `Axis` читається білдером, `Group` рендериться `FlowPanel`; ширини й розтяжність — класи домену в стилях. `title` у мові поки не оголошено.
- Перевірено на живій формі: смуга з трьох `Ref` вирівнюється сама, `Memo` забирає рядок, `Date`/`Number` — по вмісту.
- Корінь (`FormMetadata`) розкрою не має — `Body` завжди вертикальний стек.
- Обидві колекції дітей (`Fields`, `Elements`) присутні на кожному вузлі фізично; правило «тип не обирає між ключами» тримає документ і валідатор, а не тип.
- Типи — `record` з `init`-властивостями (не positional: Newtonsoft вередує), колекції read-only, `Equals`/`GetHashCode` кидають `NotSupportedException` — вузли AST не value-об'єкти.

## Відкрите

1. 🟡 **`DataGrid` / `Pager` / `Filters` як ролі.** У генераторі вони є, у словнику `is` вище — ні. Виводити таблицю списку з collection-scope не можна (групи над колекцією не існує — «Запис і колекція — два вузли»), а пейджер і фасети — chrome, виводити їх нізвідки. Вирішувати, коли index-форма писатиметься руками, а не будуватиметься за замовчуванням.
2. 🟡 **Порядок при заданих одночасно `fields` і `elements`.** Вкладеність працює (`elements` є на кожному вузлі), і саме нею робиться вся двовимірність. Але якщо в групі задані обидві колекції — порядок між полями й підгрупами не визначений. Або одне з двох забороняється валідатором, або порядок фіксується правилом. До появи реального випадку — не вирішувати.
3. **Обчислювані поля — у metadata, не у формі; закрито.** Вага справді переїхала на вирази, але expression-DSL не знадобився: вираз пишеться JS-рядком (`rules.computed`) і перевіряється Jint при `a2 validate` 🚧 — [rules.md](rules.md). Форма таких полів не оголошує, лише виводить.
4. **Умовна поведінка поля — закрито.** Носій знайдено, і він один: блок **`rules`** у metadata ([rules.md](rules.md)). `visible` — мапа «поле → JS-вираз», що компілюється в reactive computed property (`$<Field>Visible`); `required` — список імен, а умова стоїть над правилами (`when`), не всередині правила. Розподіл «носіїв два, критерій — де зуби» скасовано: він обирав дім по споживачу, а не по декларації. Статичного `visible: false` не буде: приховати безумовно = прибрати поле зі складу форми. `readonly` у цьому переліку не бере участі взагалі — див. розділ «`readonly`»: він runtime-прапор запиту, а не build-time факт.
5. 🟡 **Властивості index-форми.** У старому блоці це були `columns` / `search` / `filters` / `sort` / `totals`. Перші дві виражаються складом `fields` у відповідних вузлах; `sort` і `totals` відповідника не мають узагалі. Розбирати разом із питанням 1 — обидва про те, з чого складається форма списку.
