# Materialize — свій екран над згенерованими даними

Папка ендпоінта може тримати **обидва** файли. `metadata.json` володіє даними: SQL, деплой, команди. `model.json` володіє екраном: `view`, `template`, і все, що він умів завжди — roles, permissions, popups. Одиниця — **дія**: `index` на процедурі, `edit` на шарі метаданих, обидві над однією таблицею, яку деплоїть один файл.

Матеріалізація — це отримати згенерований екран текстом, щоб правити далі руками. Команда: `a2 meta materialize <endpoint> <action> view|template`, формат виводу — [cli.md](cli.md).

## Перемикач — значення `model`, не окремий ключ

`model` у `model.json` відповідає «звідки дані» чотирма способами, і всі в одному слоті:

| `model` | Дані |
|---|---|
| `""` | немає — екран без моделі |
| `"Agent"` | процедури `[schema].[Agent.Load]` / `.Update` / `.Delete` |
| `"$sql:key"` | текст запиту за ключем |
| `"$meta"` | шар метаданих **цієї папки** — `metadata.json` поруч |

`$` — ознака платформного значення, не імені. Наслідується від кореня до дії, як `model` завжди наслідувався:

```json
{
	"model": "$meta",
	"dialogs": {
		"edit": { "view": "edit.dialog" }
	}
}
```

`index` і `browse` не написані → синтезуються, все з метаданих. `edit` → SQL з метаданих, view свій, template згенерований. Кожен з `view`/`template` береться **окремо**: написаний — з файлу, відсутній — генерується.

Адреса ендпоінта — папка, і `model.json` її не повторює. Жодного `meta`, `schema`, `table` заради маршрутизації.

## Стан, який видно з файлів

| `model.json` | Що править LLM |
|---|---|
| відсутній | тільки `metadata.json` — усе згенероване |
| `"model": "$meta"`, дія без `view`/`template` | `metadata.json` (`forms`, `rules`) |
| дія з `"view": "edit.dialog"` | файл `edit.dialog.vxaml` — екран; `metadata.json` — дані |
| дія з `"template": "edit.template"` | файл `edit.template.ts` — поведінка; `metadata.json` — дані |
| дія з `"model": "Agent"` (ім'я поверх кореневого `$meta`) | процедури + свої `view`/`template` — ця дія ejected цілком |

Жодного `// generated` у файлах: файл є ⇔ матеріалізований ⇔ правимо вільно. `model.json` каже, який файл платформа читає.

## Дві сходинки, друга без сітки

1. **`forms` у `metadata.json`** — оголошена форма. Імена резолвляться проти shape при завантаженні: опечатка роняє ендпоінт, не екран. Замінює дефолт цілком, по частинах не дописується.
2. **`view` у `model.json`** — сирий xaml. Біндиться рядками: перейменоване поле мовчки рендериться порожнім. Перевіряється тільки `a2 view validate`.

Template дорожчий за view: у згенерований скомпільовані **правила** — required, computed, inherit, totals, стан табів. Свій template їх втрачає, і правило, дописане в `metadata.json` пізніше, до нього не доїде. Тому матеріалізований текст — початок, а не альтернатива: починати з нуля тут майже ніколи не те, чого хочеться.

## Materialize

```
a2 meta materialize catalog/agent edit view       → catalog/agent/edit.dialog.vxaml
a2 meta materialize catalog/agent edit template   → catalog/agent/edit.template.ts + edit.d.ts
```

- **Ніколи не перезаписує.** Файл є → відмова з іменем, і виклик пише все або нічого. Ще раз — це «видалити файл і запустити».
- **Виняток за власником:** `<action>.d.ts` — типи моделі, compile target shape. Перезаписується щоразу, руками не правиться. Template імпортує його з `./<action>`.
- **`model.json` не редагується.** Це файл автора. Команда повертає фрагмент (`modelJson` у відповіді); LLM зливає його в файл сам — або створює файл із самого фрагмента, якщо файлу не було.
- **`browse template` — відмова.** Browse виконує template від index; матеріалізуйте `index template` і напишіть `"template": "index.template"` під `browse`.
- `showtrans` і `print` не матеріалізуються — це не форми, вони виводяться з декларації.

Що записано — те платформа й рендерила: той самий генератор, з типами. Перший diff після правки читається.

## Відкат

Команди немає, бо стан — це файли. Видалити `edit.dialog.vxaml` і прибрати `"view"` з `model.json` — платформа знову генерує. Залишити файл, але прибрати ключ — файл лежить мертвим, платформа його не читає.

## Коли матеріалізувати

| Задача | Дія |
|---|---|
| Приховати/додати поле, змінити розкладку в межах опису | `forms` у `metadata.json` — без матеріалізації |
| Кастомна кнопка, popup, visibility-логіка, нестандартна розкладка | `materialize … view`, далі правимо `.vxaml` |
| Обробник події, обчислення, якого немає в `rules` | `materialize … template`, далі правимо `.ts` |
| Складний SQL | `model: "Agent"` на дії + процедури руками; або `post: { sql }` у `metadata.json` для проводок |

**Не матеріалізувати** заради типових випадків — `metadata.json` + runtime покривають їх, і кожен матеріалізований файл перестає отримувати те, що платформа навчиться робити далі.

## Validation

`.vxaml` — `a2 view validate <endpoint>/<action>.view|dialog`. `.ts` — збірка проєкту (tsc), типи в `<action>.d.ts` поруч.
